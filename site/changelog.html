Формат — Keep a Changelog, версии — по SemVer. До 1.0 API может меняться между минорными версиями; каждое такое изменение описано здесь.

[Unreleased]#

[0.4.0] — 2026-11-25#

Ревизия API 3 и ревизия событий 2. Логика ревизий 0, 1 и 2 работает с этим движком; новым операциям нужен #[sortie::mission(api_rev = 3)], событию AirbaseOwnerChanged — ещё и event_rev = 2. Что изменилось в поведении для любой логики и где нужна правка кода — в «Совместимости». Главное: метки F10 больше не останавливают часы сессии и таймеры; пока в сессии нет игроков, спавн идёт в темпе моста, а не 2 группы в секунду; время DCS оплачивают два бюджета писателя (чтения и тяжёлые вызовы), и отказ по лимиту называет лимит и когда повторить. Ещё — Web API движка, аэродромы и склады второй волны широкого API, задачи и маршрут наземных групп. Остальное из второй волны (состояние юнитов, обнаружение, слежение Watch, поздняя активация, правила слотов и другое) — в 0.5.0. В живой DCS ничего из этого ещё не проверялось.

Добавлено#

  • Web API: движок отдаёт HTTP/JSON для сайта сервера и сторонних приложений (страница Web API). Выключен, пока владелец не задаст адрес в engine.toml: [http] listen = "127.0.0.1:50780", там же cors_origins, max_body_bytes, actions_per_s. Чтение из зеркала мира, без DCS и без логики: GET /api/v1/session (сессия, миссия и сборка, модельное время, пауза, связи, версии), GET /api/v1/world (юниты, группы, статики, аэродромы; фильтры coalition и category), GET /api/v1/world/units/{eid}, GET /api/v1/players (игроки и их юниты, без UCID), GET /api/v1/events (Server-Sent Events: бои, взлёты и посадки, игроки, пауза; id события — <session>:<seq>, переподключение с Last-Event-ID продолжает из журнала движка, а что журнал уже не держит, называет gap). JSON — собственные стабильные формы (snake_case, коалиция "red" / "blue" / "neutral", точки {x, y, z} в метрах DCS), ошибки — {"error": {"code", "message"}} с HTTP-статусом.

  • Каждый запрос Web API несёт Authorization: Bearer <токен> из tokens.toml, как gRPC; читает любая роль. Токен нужен всегда, и с sortied --dev тоже: --dev пускает локальные программы без токена только в gRPC, потому что по HTTP программу на той же машине не отличить от страницы в её браузере или от обратного прокси. Если [http] включён, а в tokens.toml нет ни одного токена, sortied предупреждает при старте, что Web API откажет в каждом запросе.

  • Роль токена operator: читает и вызывает действия логики через Web API, в gRPC — только чтение.

  • Документы логики для сайта (ревизия API 3, страница Web API): ctx.publish("front", &значение) пишет любое Serialize в JSON и завершается, когда движок сохранил документ (sortie::publish::Published { rev, updated_unix_ms, changed }; те же байты ещё раз ничего не меняют, changed == false), ctx.unpublish(имя) убирает документ и отвечает, был ли он. Документ принадлежит логике (её имени), а не сессии: он переживает конец сессии, перезапуск логики и движка (лежит в sortie.db). Движок отдаёт документы сам, не трогая ни логику, ни DCS: GET /api/v1/docs (список: logic, name, rev, updated_unix_ms), GET /api/v1/docs/{logic}/{name} (JSON как есть, ETag — "<эпоха>-<rev>", 304 на If-None-Match; эпоха — случайная метка базы движка, так что после перезапуска движка без базы старый ETag не совпадёт с новым содержимым), GET /api/v1/docs/{logic}/{name}/events (Server-Sent Events: документ сейчас и после каждого изменения, id — <эпоха>-<rev>, unpublished, когда его нет). Правила: имя — 1–64 байта a-z0-9_-, документ — до 256 КиБ JSON, у логики — до 64 документов; иначе Error::Invalid. Протокол: StateOp.publish (PublishDoc), StateOp.unpublish (UnpublishDoc), ответ StateResult.published (PublishedDoc).

  • Действия логики для сайта (ревизия API 3, страница Web API): ctx.api().action("send_cap")? объявляет действие и возвращает поток его запросов (sortie::api::ActionRequests, next().await). Сайт или стороннее приложение с токеном роли operator (или admin) вызывает его POST /api/v1/actions/{logic}/{action} с JSON в теле; движок передаёт запрос логике по её потоку, и её ответ становится ответом: req.reply(&значение) — 200 с JSON (до 1 МиБ), req.fail(статус, текст) — 400–499, code refused; запрос, брошенный без ответа, SDK отвечает 500 unanswered. У запроса — req.json::<T>(), req.body(), имя токена req.token() и роль req.role(). Движок ждёт ответа 10 секунд (sortie::api::ACTION_TIMEOUT; потом 504 timeout), и запрос, который столько пролежал в очереди логики, SDK ей уже не отдаёт, а отвечает unanswered сам. Движок отвечает 404 на действие, которого никто не объявлял, 503 unavailable, пока логика не подключена или не объявила его в этой сессии, 429 rate_limited сверх [http] actions_per_s вызовов токена (считает сам токен, не имя; с Retry-After), 413 сверх max_body_bytes, 400 на тело не в JSON; GET /api/v1/actions — что объявлено сейчас. Каждый вызов пишется в журнал движка (токен, логика, действие, статус, время; без тела). Объявления живут, пока жив поток и идёт сессия; после перезапуска логики функция миссии объявляет их снова. Правила: имя — 1–64 байта a-z0-9_-, до 64 действий, у действия один поток; иначе Error::Invalid. Протокол: LogicUp.actions (ActionSet), LogicDown.action (ActionCall), LogicUp.action_reply (ActionReply, ActionRefusal).

  • Аэродромы (ревизия API 3, страница Аэродромы): ctx.airbase_control([airbases::X, ..]).owner(Coalition::Red).auto_capture(false) .radio_silent(true) меняет у 1–32 аэродромов владельца, автозахват DCS и радиомолчание за один кадр DCS (сначала автозахват, потом владелец, потом радио) и читает каждую базу обратно; больше баз — несколько команд (sortie::cmd::MAX_AIRBASES = 32: около 11 вызовов DCS на базу в одном кадре, стоимость ещё не измерена). Результат sortie::cmd::AirbasesControlled { bases }: по одной AirbaseControlled { eid, name, before, after } на базу, before / after — AirbaseState { owner, auto_capture, radio_silent }, своя ошибка базы — error() (Error::Gone, Error::Lua), остальные базы выполняются. Новый владелец сразу в ctx.world(), и захват, который DCS подняла раньше команды, но движок получил после её ответа, его не откатывает (движок сравнивает их место в порядке событий DCS). Движок проверяет весь список до отправки: базы нет в мире, база дважды, пустой список или длиннее 32, нечего менять — Error::Invalid с её именем, в DCS ничего не уходит. Ключ — как у любой меняющей команды. Возможность caps::AIRBASE_CONTROL включена по умолчанию; живая проверка AWC-T20 (ещё не измерена). FakeDcs: airbase_auto_capture(имя), airbase_radio_silent(имя); сырые Airbase.autoCapture, setRadioSilentMode и их чтения работают с тем же состоянием. Протокол: Command.body.airbase_control = 36 (AirbaseControl), Reply.airbase_control = 11 (AirbasesControlled, AirbaseControlResult, AirbaseControlState); операция слоя Lua airbase_control.

  • Событие смены владельца аэродрома (ревизия событий 2, страница Аэродромы): ctx.events().of::<v1::AirbaseOwnerChanged>() — ровно одно событие на каждую смену владельца в мире движка, что бы о ней ни сообщило: cause — Captured (DCS подняла S_EVENT_BASE_CAPTURED; сразу после её BaseCaptured), Control (ctx.airbase_control; раньше ответа команды), Discovered (снимок мира после разрыва связи или потери событий или запрос состояния нашёл другого владельца). Поля airbase (база после смены), previous (прежний владелец, Unspecified — не знал), owner. Сообщение о том, что мир уже знает, второго события не даёт; захват, который DCS подняла раньше чтения базы, а движок получил позже его ответа, тоже (только его BaseCaptured); первый снимок сессии ничего не публикует. Мир знает нового владельца, когда событие пришло. Владельца, которого другой скрипт сменил без события, мир узнаёт только при чтении: логика, которой это нужно, опрашивает ctx.airbases_state(..). Фильтры .airbase(..), .cause(..), .coalition(..) (новый владелец). То же событие — в GET /api/v1/events как airbase_owner_changed. FakeDcs: capture_airbase(имя, коалиция) (захват, как его сообщает DCS), set_airbase_coalition_silently(имя, коалиция) (без события), lose_events(n) (движок снимает мир заново), hold_events() / release_events() (события DCS ждут в очереди моста, ответы команд уходят сразу). Живая проверка AWC-T21 (ещё не измерена). Протокол: Event.kind.airbase_owner_changed = 55 (AirbaseOwnerChanged, OwnerChangeCause), EVENT_KIND_AIRBASE_OWNER_CHANGED = 41.

  • Запросы аэродромов (ревизия API 3, страница Аэродромы): стоянки, полосы и состояние, ничего не меняют в DCS и не требуют ключа. Удаление несуществующей метки — успех (ABSENT) для логики, объявившей api_rev = 1; логика 0.1.0 (ревизия 0) получает sortie::invalid, как раньше. Метки и рисунки убираются при конце сессии, если в ней реестром пользовалась команда ревизии 1 или новее; сессия только логик 0.1.0 оставляет метки и меню, как 0.1.0.
  • Логика 0.1.0 видит события и команды в DCS как раньше (проверка CMP-1): UnitGone с причиной GONE_REASON_REPLACED приходит ей как GONE_REASON_DESPAWNED; поток команд в DCS для examples/op_north совпадает с 0.1.0 побайтно.
  • Мир: гибель пилота (S_EVENT_PILOT_DEAD) больше не делает юнит мёртвым — DCS присылает её, пока самолёт ещё летит; событие по-прежнему Dead. Логике API ревизии 0 (по умолчанию у #[sortie::mission]) оно приходит с dead = true, как в 0.1.0, и её мир (ctx.world()) держит юнит мёртвым, как в 0.1.0; живым его видит логика ревизии 1 и подписка на мир. Выход игрока из юнита (S_EVENT_PLAYER_LEAVE_UNIT) убирает игрока из EntitySnap.player: юнит пропадает из players() и из подписки на мир «только игроки», а UnitGone.last_known после выхода игрока не называет. Это видно и логике 0.1.0.
  • Unknown.fields сохраняет вид 0.1.0: только прежние двенадцать ключей. Ключи DCS сверх них (comment, ключи новых сборок, объекты под другими ключами) есть только в ctx.
  • WeaponSnap.eid больше не 0 (это видно и логике 0.1.0): по нему сопоставляются Shot, Hit и Kill одного оружия. Безымянный участник события, которого нет в мире (катапультировавшийся пилот, кресло), больше не попадает в мир движка; его снимок несёт Eid пилота. Реплика SDK этой версии не добавляет в мир ни оружие, ни такие объекты из событий.
  • У TypedEvents::of::<v1::Unknown>() фильтры in_group и coalition теперь находят события (раньше у Unknown не было субъекта, и они не пропускали ничего).
  • Menu (ctx.menu(..)) тоже регистрируется: в реплике мира — дерево из одного пункта с именем sortie:menu/<ident>/..; повтор ничего не делает, как и раньше; изменённая надпись заменяет пункт; ключ команды не используется. Исправлено: копия команды .per_group() снимается, когда слот группы пустеет, и ставится следующему игроку, в том числе в динамический слот с новым id группы (раньше слой Lua помнил каждый id группы навсегда и не ставил команду заново).
  • sortie::Failure получил поле capability: код, который собирает Failure { .. } без ..Failure::default(), должен его добавить.
  • Сырые вызовы trigger.action.markTo* / *ToAll / setMarkup* / removeMark есть в каталоге, но устарели в пользу ctx.map() и отклоняют id от 7 100 000.
  • GroupSel и UnitSel переехали из commands.proto в common.proto (пакет sortie.v1, номера полей те же, проводной формат не изменился). В Rust пути прежние (sortie::proto::v1::GroupSel); в Python стабы теперь в common_pb2, а не в commands_pb2. buf breaking проверяет совместимость на уровне пакета.

Безопасность#

  • Слой Lua при старте миссии выключает модальное окно ошибок Lua DCS (env.setErrorMessageBoxEnabled(false)): ошибка в любом скрипте миссии больше не останавливает выделенный сервер до щелчка по окну.

  • Вызовы DCS: ключи перечислений проверяются везде, где стоят, и внутри таблиц: форма <таблица>.<КЛЮЧ>, таблица — одна из названных каталогом (world.VolumeType для объёмов); у параметра any ключей нет; в окружении хуков — только таблицы слоя sortie.*. Слой принимает путь только целиком. Пакет ctx.dcs().batch() оплачивает в лимите писателя каждый вызов. Предел в 256 созданных объектов (лазерных пятен) на сессию проверяется до вызова DCS: отклонённый вызов не оставляет в DCS пятна, которое никто не снимет.

  • Запись [[calls.call]] владельца с классом heavy и именем не из get/is/has считается изменяющей и выключена, пока её не включат (enabled = true или sortied --dev). sortied --dev теперь действительно включает изменяющие записи владельца (раньше включал только встроенные, а отказ советовал --dev); enabled = false записи и список disable сильнее --dev.

  • net().player_info(id, атрибут) принимает только атрибуты id, name, side, slot, ping, ucid, lang: другое имя — Error::Invalid, ipaddr — по-прежнему Error::Rejected. Раньше отклонялась одна точная строка ipaddr, а строка вроде "ipaddr\0" доходила до DCS; как DCS читает такое имя, неизвестно.

  • engine.toml [calls]: в enable и disable метод называется путём своей записи каталога (Object.destroy). Имя через класс-наследник (Unit.destroy, Weapon.destroy) раньше молча переключало запись для всех классов; теперь это ошибка при старте sortied, в сообщении названа запись.

  • Мост не передаёт результат, который не смог преобразовать целиком (больше 200 000 значений или 16 МиБ строк): команда получает sortie::bridge_fault с этим объяснением, а не результат с пропусками. Нужны новые DLL моста и слой Lua (sortie install, перезапуск DCS).

  • Сырые таблицы больше не несут код в DCS. Task::raw(..), .raw(..) статика и аргументы ctx.dcs() с id = "Script" / "ScriptFile", строкой condition (условие ControlledTask), строкой command в params или строкой file отклоняются с sortie::rejected, capability = "dev_eval", и путём внутри таблицы. Это касается и логик 0.1.0: в 0.1.0 такая задача выполняла Lua в DCS без --dev-eval. NaN и бесконечность в сырых таблицах и в числах команд 0.1.0 (точка спавна, орбита, дым, метка, высота земли) теперь sortie::invalid (раньше молча превращались в null или в значение по умолчанию). С sortied --dev-eval код из команды токена admin проходит с предупреждением в журнале (Проверка сырых таблиц).

  • engine.toml [calls] строже: нельзя расширить встроенный clamp, поменять поля, из которых генерируются обёртки, закрыть унаследованный метод новой записью (Unit.destroy) и добавить путь не от таблиц DCS (_G, string); _G в списке NEVER. Такой файл останавливает sortied при старте.

Что есть#

  • Крейт sortie: логика миссии как асинхронная программа на Rust. #[sortie::mission] и sortie::main! дают точку входа и весь main.rs. Через Ctx логика читает мир из локальной реплики (ctx.wait_until(|w| ...), события) и отдаёт команды: сообщения, флаги, опции и задачи групп, спавн по шаблонам, меню F10, дым. Есть состояние в движке, таймеры и once_per_turn. Каждая команда — future, который завершается, когда DCS её выполнила; ошибки называют строку вызова.
  • sortie-build и sortie::include_scenario!: типизированные символы сценария из scenario.lock.json (groups::..., zones::..., templates::..., flags::...). Опечатка в имени — ошибка компиляции, а не сбой в DCS.
  • Генератор sortie-gen (Python 3.11+, pydcs 1.0.0): сценарий в коде, .miz, manifest и lock; регистрация и запуск сборок у движка, поток событий, итоги сессии; команды lobby и adopt.
  • Схемы protobuf sortie.v1 (API движка) и sortie.manifest.v1.
  • Шаблон проекта миссии (template/) и пример examples/op_north.
  • Документация на русском, навыки для ИИ-агентов (agents/) и сайт с документацией.

  • Тестов логики без DCS. #[sortie::test] и FakeDcs появятся в SDK 0.2; сейчас #[sortie::test] даёт ошибку компиляции с пояснением. Логику проверяют на живой DCS с sortied --dev.
  • Горячей перезагрузки логики (sortie dev).
