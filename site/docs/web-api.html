Web API#

Движок умеет отдавать HTTP/JSON: из него сайт сервера строит живую карту и страницу кампании, стороннее приложение читает, что происходит в миссии, и просит логику что-то сделать (например, отправить группу в точку). Это тот же движок sortied, те же токены, что у gRPC, и тот же мир, который видит логика. Запросы на чтение не доходят ни до DCS, ни до логики: движок отвечает из своего зеркала мира, журнала событий и хранилища, где лежат документы, которые опубликовала логика. Вызов действия движок передаёт логике, которая его объявила, и отвечает её ответом.

Что есть сейчас:

ЗапросЧто отдаёт
GET /api/v1/sessionсессия, миссия и сборка, модельное время, пауза, связи с DCS, версии
GET /api/v1/worldюниты, группы, статики, аэродромы; фильтры coalition и category
GET /api/v1/world/units/{eid}один юнит или статик
GET /api/v1/playersподключённые игроки и юниты, в которых они сидят
GET /api/v1/eventsпоток событий (Server-Sent Events)
GET /api/v1/docsдокументы, которые опубликовали логики
GET /api/v1/docs/{logic}/{name}один документ: JSON, как его опубликовала логика
GET /api/v1/docs/{logic}/{name}/eventsпоток изменений документа (Server-Sent Events)
GET /api/v1/actionsдействия, которые объявили подключённые логики
POST /api/v1/actions/{logic}/{action}вызов действия логики: JSON туда, её JSON обратно (роль operator или admin)

Команд DCS по HTTP нет и не будет: ни спавна, ни управления сервером, ни записи состояния, ни регистрации и запуска миссий. Сайт читает и может вызвать действие логики; что от этого изменится в игре, решает логика.

Включение#

API выключен, пока владелец движка не назовёт адрес в engine.toml (страница Эксплуатация):

# Saved Games\DCS\Sortie\engine.toml
[http]
listen = "127.0.0.1:50780"                 # нет ключа или пустая строка — API выключен
cors_origins = ["https://map.example.org"] # страницы этих сайтов читают API из браузера
max_body_bytes = 65536                      # больше — ответ 413
actions_per_s = 20                          # на токен

sortied читает файл при старте: после правки перезапустите его. Ошибка в [http] (адрес без порта, origin с путём) не даёт движку стартовать и называет ключ.

Движок говорит обычным HTTP, без TLS. Держите listen на 127.0.0.1, а в интернет выпускайте через обратный прокси с HTTPS (nginx, Caddy) на той же машине. Если listen смотрит за пределы машины, sortied пишет предупреждение: тогда токен защищает всё, а ходит он открытым текстом.

Токены#

Каждый запрос несёт заголовок Authorization: Bearer <токен> с токеном из tokens.toml (см. Эксплуатация). Читать может любая роль. Для сайта, который только читает, заведите отдельный токен роли observer. Вызывать действия логики может роль operator (она же читает, а в gRPC больше ничего не может) или admin.

curl -H "Authorization: Bearer 6f1c..." http://127.0.0.1:50780/api/v1/session

Токен нужен всегда, и с sortied --dev тоже: --dev пускает локальные программы без токена только в gRPC. По HTTP движок не может отличить программу на той же машине от страницы в её браузере, от имени, которое ведёт на 127.0.0.1 извне, или от обратного прокси на той же машине: все они подключаются с 127.0.0.1. Для разработки заведите в tokens.toml токен, например роли admin. Если в tokens.toml нет ни одного токена, sortied при старте предупреждает, что Web API откажет в каждом запросе.

Токен не должен попадать в браузер посетителя. Обычная схема: сервер сайта ходит в API со своим токеном и отдаёт страницам то, что им можно видеть. API отдаёт всё, что знает движок, обо всех коалициях; что показывать на публичной карте (например, только свои юниты), решает сайт.

Ошибки#

Ошибка — JSON с HTTP-статусом:

{"error": {"code": "no_session", "message": "no mission session is running"}}

Сообщение message — для человека: в нём сказано, что не так и что принимается.

CORS#

Пока cors_origins пуст, движок не шлёт заголовков CORS, и браузер не даст странице другого сайта прочитать ответ. Origin пишется как схема://хост[:порт] без пути ("https://map.example.org", "http://localhost:3000"); "*" — любой сайт (токен ему всё равно нужен). Preflight (OPTIONS) от origin из списка движок отвечает без токена: методы GET, POST, OPTIONS, заголовки authorization, content-type, last-event-id. Каждый ответ такому origin, включая ошибки, несёт Access-Control-Allow-Origin.

Формат данных#

  • Ключи — snake_case. Коалиция — "red", "blue" или "neutral". Категория — "airplane", "helicopter", "ground_unit", "ship", "structure", "static", "weapon", "scenery", "base", "cargo".
  • Точка — {"x": ..., "y": ..., "z": ...} в метрах DCS: x — север, y — высота над уровнем моря, z — восток. Скорость — в тех же осях, м/с. Курс — heading_rad, радианы.
  • Широты и долготы API не отдаёт. Если они нужны карте, логика пересчитывает точки сама и публикует их в своём документе (см. Документы логики).
  • Поле без значения в ответе не пишется: нет pos — позиция неизвестна, нет player — юнитом управляет ИИ.
  • eid — целое число, идентификатор объекта в мире Sortie (тот же, что у Entity.eid в логике). Оно меньше 2^53, поэтому в JavaScript читается точно. Номера начинаются заново с каждой сессией.

/api/v1/world?coalition=blue
/api/v1/world?coalition=red&category=ground_unit,ship

GET /api/v1/world/units/{eid} отдаёт один объект в том же виде, что элемент units (или statics). Нет такого eid в текущей сессии — 404 not_found.

События#

GET /api/v1/events — поток Server-Sent Events: соединение остаётся открытым, каждое событие движка — одно событие SSE.

id: 01JF3Q4W8V0Y5N2C7G6KQ1M9TB:418
data: {"seq":418,"session":"01JF3Q4W8V0Y5N2C7G6KQ1M9TB","model_time":1840.2,"dcs_event":"dead","kind":"dead","initiator":{"eid":4294967310,"name":"SAM North-3","type_name":"S-300PS 5P85C ln","coalition":"red","category":"ground_unit","dead":true}}
  • data — JSON события: seq (номер в журнале сессии), session, model_time, wall_unix_ms (часы движка), dcs_event (из какого события DCS: "crash", "runway_takeoff"), kind и поля этого вида. Поле event: у SSE не задаётся: все события приходят как message, вид — в kind.
  • id — <session>:<seq>. Номера seq идут по журналу сессии, общему для всех подписчиков, поэтому в потоке бывают пропуски: это события, которых поток не показывает (чат, отфильтрованные виды), а не потери. Потери поток называет только событием gap.
  • Пока событий нет, раз в 15 секунд приходит комментарий (строка с :), чтобы прокси не закрывал соединение.

Фильтр coalition= у airbase_owner_changed смотрит на нового владельца. Чат игроков, метки F10, нажатия меню, ресурсы и возможности движка, сырые события DCS поток не показывает: они остаются логике и клиентам gRPC.

Переподключение. Браузерный EventSource и большинство библиотек SSE сами переподключаются и шлют заголовок Last-Event-ID с последним полученным id. Движок продолжает с события после него из своего журнала; если тем временем началась новая сессия, сначала идёт остаток старой, затем новая с начала. Если журнал в памяти этих событий уже не держит (движок перезапускали), поток начинается с gap, который называет потерянные номера: тогда перечитайте мир через /api/v1/world. Last-Event-ID важнее from_seq.

curl -N -H "Authorization: Bearer 6f1c..." "http://127.0.0.1:50780/api/v1/events?kinds=dead,kill"

Браузерный EventSource не умеет слать заголовок Authorization, поэтому с токеном поток читает сервер сайта. На Node.js 18 и новее хватает fetch:

const res = await fetch("http://127.0.0.1:50780/api/v1/events?kinds=dead,kill", {
  headers: { Authorization: `Bearer ${process.env.SORTIE_TOKEN}` },
});
const decoder = new TextDecoder();
let buf = "";
for await (const chunk of res.body) {
  buf += decoder.decode(chunk, { stream: true });
  let end;
  while ((end = buf.indexOf("\n\n")) >= 0) {
    const frame = buf.slice(0, end);
    buf = buf.slice(end + 2);
    const data = frame.split("\n").filter((l) => l.startsWith("data: ")).map((l) => l.slice(6)).join("");
    if (data) console.log(JSON.parse(data));
  }
}

Документы логики#

Сайту часто нужно то, чего в мире DCS нет: состояние кампании, линия фронта, счёт, точки в широте и долготе. Это знает логика, и она публикует такие данные как именованные JSON-документы (ревизия API 3). Движок хранит документ и сам отдаёт его по HTTP: запрос сайта не доходит ни до логики, ни до DCS, поэтому частые запросы ей ничем не мешают.

/// Что читает карта сайта: `GET /api/v1/docs/<логика>/front`.
#[derive(Serialize)]
pub struct Front {
    pub armor_left: usize,
    /// Широта и долгота центра бронегруппы, градусы.
    pub armor_at: Option<[f64; 2]>,
}

#[sortie::mission(api_rev = 3)] // ctx.publish — API ревизии 3
pub async fn run(ctx: Ctx<MyMission>, _start: Start) -> sortie::Result<()> {
    loop {
        let (armor_left, center) = {
            let world = ctx.world();
            let armor = world.group(&groups::ARMOR);
            (armor.alive_count(), armor.center())
        };
        let armor_at = match center {
            Some(c) => {
                let (lat, lon, _alt) = ctx.dcs().coord().lo_to_ll(c.alt(m(0.0))).await?;
                Some([lat, lon])
            }
            None => None,
        };
        // Те же данные ещё раз ничего не меняют: rev прежний, поток документа молчит.
        let front = Front {
            armor_left,
            armor_at,
        };
        ctx.publish("front", &front).await?;
        ctx.sleep(secs(10)).await;
    }
}
  • ctx.publish(имя, &значение) пишет значение в JSON (serde) и завершается, когда движок сохранил документ. Ответ — Published { rev, updated_unix_ms, changed }; changed == false значит, что у движка уже были ровно эти байты и ничего не изменилось. Поэтому публиковать по таймеру можно без оглядки: пока данные те же, сайт не видит изменений.
  • Документ принадлежит логике, а не сессии: он переживает конец сессии, перезапуск процесса логики и перезапуск движка (лежит в sortie.db рядом с состоянием). После перезапуска сайт читает последний опубликованный документ, а логика просто публикует снова, когда данные поменяются.
  • ctx.unpublish(имя) убирает документ; ответ — был ли он:
let removed = ctx.unpublish("front").await?; // false — такого документа не было
  • Правила, иначе Error::Invalid и ничего не сохраняется: имя — от 1 до 64 байт из a-z, 0-9, _ и -; документ — не больше 256 КиБ JSON; у одной логики не больше 64 документов (новое имя сверх них — ошибка, старые меняются как обычно).
  • Документы лежат под именем логики — именем её программы (Attach.logic, обычно имя бинарника). Оно становится частью пути, поэтому публиковать может логика, чьё имя — от 1 до 64 байт из A-Z, a-z, 0-9, ., _ и -.
  • Логика ревизии ниже 3 получает Error::Revision, движок старее — Error::EngineTooOld; в обоих случаях ничего не отправлено.

  ]
}

По логике, затем по имени. rev — номер изменения: он растёт с каждой публикацией любого документа движка и не повторяется, даже если документ убрали и опубликовали снова, — пока движок хранит своё состояние в sortie.db. Движок, который держит состояние только в памяти (--db memory или без папки Saved Games), после перезапуска считает снова с 1. Поэтому содержимое документа называет не rev, а ETag (ниже): в нём перед rev стоит эпоха — случайная метка базы, у каждой новой базы и у каждого запуска без базы своя. updated_unix_ms — когда движок сохранил это содержимое (его часы).

Документ#

GET /api/v1/docs/{logic}/{name} отдаёт JSON ровно в том виде, в каком его опубликовала логика (Content-Type: application/json), с заголовками ETag: "<эпоха>-<rev>" (например, "k3q9x2mb-57") и Cache-Control: no-cache. Нет такого документа — 404 not_found; имя не по правилам — 400. Один ETag — одно содержимое, и после перезапуска движка тоже.

Чтобы не тянуть документ, который не менялся, пришлите его ETag в If-None-Match: пока документ тот же, ответ — 304 Not Modified без тела. Браузер делает это сам: ответ помечен Cache-Control: no-cache, и перед тем как взять документ из кэша, браузер спрашивает движок.

curl -i -H "Authorization: Bearer 6f1c..." -H 'If-None-Match: "k3q9x2mb-57"' \
  http://127.0.0.1:50780/api/v1/docs/op_north_logic/front

Поток документа#

GET /api/v1/docs/{logic}/{name}/events — Server-Sent Events: сначала документ как он есть, затем он же после каждого изменения.

id: k3q9x2mb-57
data: {"armor_left":4,"armor_at":[44.61,40.08]}

event: unpublished
data: {"logic":"op_north_logic","name":"front"}
  • Событие без поля event: (то есть message) — документ: data — его JSON, id — <эпоха>-<rev>, его ETag без кавычек.
  • event: unpublished — документа нет: его убрали, или он ещё не опубликован, когда поток открылся. Когда логика опубликует его снова, придёт обычное событие.
  • Изменения, которые идут подряд быстрее, чем клиент читает, могут прийти одним последним: поток всегда догоняет текущий rev, но промежуточные может пропустить.
  • Переподключение с Last-Event-ID (браузерный EventSource шлёт его сам) не присылает документ снова, если он не изменился; иначе первым придёт текущий. id другой эпохи (движок перезапустился без базы) — как будто ничего не получено: документ придёт сразу. id не в виде <эпоха>-<rev> — 400.
  • Раз в 15 секунд без изменений приходит комментарий (строка с :). Поток заканчивается, когда останавливается движок.

Действия логики#

Иногда сайт или стороннее приложение должны что-то изменить в игре: отправить патруль, поднять дым, начать этап кампании. Сам он команд DCS не шлёт. Логика объявляет именованное действие (ревизия API 3), сайт вызывает его запросом POST с JSON, движок передаёт вызов этой логике по её потоку, и её ответ становится ответом на запрос. Что сделать в игре и делать ли вообще, решает логика: она проверяет запрос, как любой ввод снаружи.

/// Что присылает сайт: `POST /api/v1/actions/<логика>/send_cap`.
#[derive(Deserialize)]
pub struct SendCap {
    /// Его номер заказа: повтор того же заказа (после 504) не поднимет второй патруль.
    pub order: String,
    /// Центр патруля в метрах DCS: `x` — север, `z` — восток.
    pub x: f64,
    pub z: f64,
}

/// Что получает сайт в ответе 200.
#[derive(Serialize)]
pub struct CapSent {
    pub group: String,
}

#[sortie::mission(api_rev = 3)] // ctx.api() — API ревизии 3
pub async fn dispatcher(ctx: Ctx<MyMission>, _start: Start) -> sortie::Result<()> {
    let mut send_cap = ctx.api().action("send_cap")?;
    while let Some(req) = send_cap.next().await {
        let order: SendCap = match req.json() {
            Ok(order) => order,
            Err(e) => {
                req.fail(400, e)?; // тело не подходит: 400, code "refused"
                continue;
            }
        };
        let center = MapPoint::new(order.x, order.z);
        if !zones::PATROL.contains(center) {
            req.fail(422, "the point is outside the patrol zone")?;
            continue;
        }
        let cap = ctx
            .spawn_group(templates::RED_CAP.named(format!("Red CAP {}", order.order)))
            .from_airbase(airbases::NALCHIK, StartType::Runway)
            .key(format!("send-cap-{}", order.order))
            .await?;
        cap.push_task(Task::orbit(center)).await?;
        req.reply(&CapSent {
            group: cap.name().to_owned(),
        })?;
    }
    Ok(())
}
  • ctx.api().action(имя) сразу объявляет действие и возвращает поток его запросов; next() отдаёт следующий запрос и None, когда сессия кончилась. Объявление живёт, пока жив поток и идёт сессия: брошенный поток и конец сессии его снимают. После перезапуска процесса логики или миссии функция миссии объявляет действия снова; в промежутке вызов получает 503 unavailable.
  • У запроса есть тело — req.json::<T>() (serde; ошибка — Error::Invalid, её текст говорит, что не подошло) или req.body() как есть, — имя токена вызвавшего req.token() и его роль req.role() ("operator" или "admin"). Пустое тело приходит как null.
  • Ответ — ровно один: req.reply(&значение) — 200 с этим JSON (не больше 1 МиБ); req.fail(статус, текст) — статус от 400 до 499 и {"error": {"code": "refused", "message": текст}}. Статусы 5xx — не логики: их ставит движок. Запрос, который логика бросила без ответа (конец цикла, ошибка ?, конец сессии), SDK сам отвечает 500 unanswered.
  • Движок ждёт ответа 10 секунд (sortie::api::ACTION_TIMEOUT), потом отвечает 504 timeout; поздний ответ уходит в никуда. Долгую работу делайте после ответа: ответьте «принято» и продолжайте в ctx.spawn, а сайт узнает результат из документа.
  • Запрос, который пролежал в очереди 10 секунд (логика не читала поток), SDK логике уже не отдаёт: вызывающий получил 504, и выполнять запрос поздно. SDK сам отвечает на него unanswered, как только приходит следующий запрос или логика вызывает next().
  • 504 не говорит, сделала ли логика своё. Поэтому пусть сайт шлёт номер заказа, а логика делает из него ключ команды (.key(..)): повтор того же вызова вернёт сохранённый результат и второй раз в DCS не попадёт.
  • Правила, иначе Error::Invalid и ничего не объявлено: имя — от 1 до 64 байт из a-z, 0-9, _ и -; у логики не больше 64 действий; у действия один поток (второй action с тем же именем, пока первый жив, — ошибка); имя логики — от 1 до 64 байт из A-Z, a-z, 0-9, ., _ и - (оно часть пути). Логика ревизии ниже 3 получает Error::Revision, движок старее — Error::EngineTooOld.
  • Каждый вызов движок пишет в журнал: имя токена, логика, действие, статус, время ответа. Тело запроса в журнал не попадает.

Список#

GET /api/v1/actions (любая роль) — что объявляют подключённые логики сейчас, по логике, затем по имени:

{
  "actions": [
    {"logic": "op_north_logic", "name": "send_cap"},
    {"logic": "op_north_logic", "name": "smoke_objective"}
  ]
}

Вызов#

POST /api/v1/actions/{logic}/{action} с токеном роли operator или admin и JSON в теле:

curl -H "Authorization: Bearer 6f1c..." -H "Content-Type: application/json" \
  -d '{"order": "a17", "x": -270645, "z": 717280}' \
  http://127.0.0.1:50780/api/v1/actions/op_north_logic/send_cap

{"group": "Red CAP a17"}
  • Ответ 200 — JSON логики как есть. Отказ логики — её статус и code refused.
  • 404 not_found — такого действия ни одна логика с этим именем не объявляла с запуска движка (после перезапуска движка — пока логика не объявит его снова). 503 unavailable — действие объявляли, но сейчас никто: логика не подключена, перезапускается или ждёт сессии; повторите позже. 500 unanswered — логика бросила запрос; 504 timeout — не ответила за 10 секунд.
  • Тело — JSON не больше max_body_bytes (иначе 413); пустое тело — null; не JSON — 400, до логики такой запрос не доходит.
  • Один токен вызывает не больше actions_per_s действий в секунду (engine.toml [http], по умолчанию 20; сразу можно столько, сколько набирается за секунду). Сверх — 429 rate_limited с заголовком Retry-After. Вызовы, которые получили 404 или 503, тоже считаются. Счёт ведётся по самому токену, а не по его имени: у двух токенов без имени или с одним именем счёт свой.
  • Со страницы в браузере вызов идёт через preflight CORS (POST, заголовки authorization и content-type разрешены для origin из cors_origins). Но токен operator в браузер посетителя не отдавайте: действие вызывает сервер сайта, а страница просит об этом его.
