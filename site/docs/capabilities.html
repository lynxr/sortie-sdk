Возможности движка#

Не каждая операция работает везде: функции DCS появляются и пропадают между сборками, слой Lua может быть старше движка, владелец движка может что-то выключить, а операция, во время которой упал DCS, уходит на карантин. Движок сводит всё это в одну таблицу возможностей. Логика получает её в Start, читает через ctx.capabilities() и может потребовать нужное заранее: тогда она не запустится там, где этого нет, вместо того чтобы упасть в редкой ветке посреди миссии.

Имена#

Имена — константы sortie::caps:

ИмяЧто это
caps::SPAWN_STATIC, caps::DRAW, caps::MENU_TREE, caps::REMOVE_JUNK, caps::DESTROY, ...типизированные операции (caps::MENU — меню F10 из 0.1.0, caps::MENU_TREE — деревья меню)
caps::SPAWN_BATCHпакет спавнов: группы и статики одной командой; владелец, выключивший spawn_static или spawn_group, отказывает и пакету с таким элементом
caps::DESTROY_WEAPONdestroy оружия в полёте и катапультировавшегося пилота по Eid
caps::DESTROY_SCENERYdestroy объекта карты: не сделано (NOT_IMPLEMENTED)
caps::QUERY_LAND_HEIGHT, caps::SERVER_SEND_CHAT, ...виды запросов и управления сервером
caps::DCS_CALL, caps::DCS_BATCHуниверсальный вызов DCS целиком (Вызовы DCS)
caps::call::mission::LAND_GET_HEIGHT = "call:mission:land.getHeight"одна функция каталога DCS API; генерируются из каталога

Состояния#

СостояниеЗначит
AVAILABLEработает
NOT_IMPLEMENTEDобъявлено, но не сделано; или слой Lua в DCS старше движка (sortie install)
MISSING_IN_DCSнужной функции нет в запущенной сборке DCS
DISABLEDвыключено владельцем движка (engine.toml), выключено по умолчанию (мутаторы каталога, dev_eval без --dev-eval) или это непроверенное чтение каталога
QUARANTINEDDCS упал, пока выполнялась операция этого вида (у универсального вызова — эта функция каталога), или мост отключил её после трёх сбоев

У каждой записи есть note — почему она не AVAILABLE. Поле live пока везде UNVERIFIED: автоматические проверки на живом DCS ещё не записывают результатов, поэтому «есть в сборке» не значит «проверено в бою».

Требовать заранее#

#[sortie::mission(api_rev = 1, requires = [caps::SPAWN_STATIC, caps::DRAW])]
pub async fn needs_statics(ctx: Ctx<MyMission>, _start: Start) -> sortie::Result<()> {
    // Сюда логика попадает, только если обе возможности AVAILABLE: иначе движок отказал в
    // Attach (AttachRejected.missing_capabilities), и миссия-функция не запускалась.
    ctx.end_session(Outcome::Draw).await
}

requires уходит в Attach.required_capabilities. Движок проверяет список при подключении и ещё раз перед Start (пробник новой сборки DCS мог что-то убрать). Отказ называет каждую недостающую возможность с её состоянием. Против движка 0.1.0, который таблицы не знает, логика с requires не запускает миссию-функцию и записывает ошибку.

Читать таблицу#

let t = ctx.capabilities();
let junk = t.is_available(caps::REMOVE_JUNK);
// Почему нет (MISSING_IN_DCS, DISABLED, QUARANTINED...): заметка движка.
let why = t.note(caps::REMOVE_JUNK).to_owned();
let height = t.state(caps::call::mission::LAND_GET_HEIGHT);
let quarantined: Vec<&str> = t
    .in_state(v1::CapabilityState::Quarantined)
    .map(|c| c.name.as_str())
    .collect();

ctx.capabilities() — копия таблицы на этот момент: таблица из Start, обновлённая событиями CapabilityChanged. Эти события приходят логике с event_rev = 1; с event_rev = 0 таблица остаётся такой, какой была в Start. Имя, которого движок не знает, читается как NOT_IMPLEMENTED. Одна запись без копии всей таблицы — ctx.capability(имя):

if let Some(c) = ctx.capability(caps::MENU_TREE) {
    // Состояние, заметка, id живых проверок (PLY-LC1, ...), с какой ревизии API.
    let _ = (c.state, c.note, c.live_checks, c.since_api_rev);
}

Отказ по возможности несёт её имя в Error::capability():

match ctx.dcs().land().height(MapPoint::new(0.0, 0.0)).await {
    Ok(h) => Ok(Some(h)),
    // Этот путь на карантине после падения DCS: capability() = Some("call:mission:...").
    Err(e @ sortie::Error::Quarantined(_))
        if e.capability() == Some(caps::call::mission::LAND_GET_HEIGHT) =>
    {
        Ok(None)
    }
    Err(e) => Err(e),
}

Откуда движок это знает#

  • Пробник. Когда слой Lua в DCS присылает таблицы чисел, движок спрашивает его, какие функции каталога и функции типизированных операций есть в этой сборке и какие операции слоя загружены. Ничего не вызывается, только поиск по имени. Отсутствующее становится MISSING_IN_DCS, недостающая операция слоя — NOT_IMPLEMENTED. Слой старше пробника (в Saved Games остался прежний слой, sortie install не запускали) отвечает, что такой операции нет; движок считает его слоем 0.1.0, и все операции волны 1 (spawn_static, draw, menu_tree, remove_junk, dcs_call, dcs_batch, все call:*) — NOT_IMPLEMENTED с подсказкой «run sortie install». Логика с requires = [...] получает отказ при подключении, а не ошибку на первой команде.
  • Владелец движка. engine.toml: [calls] включает и выключает функции каталога, [operations] disable = ["remove_junk"] выключает типизированные операции (они DISABLED, команда — Error::Rejected с capability()).
  • Карантин. Если связь с DCS оборвалась без прощания, пока выполнялись команды, а следующий мост пришёл от другого процесса DCS (то есть DCS упал и его запустили снова), вид операции, которая выполнялась, уходит на карантин (у универсального вызова — одна функция каталога, см. ниже). Считаются и команды логики, и собственные задания реестра движка: перенос дерева меню за слотом группы, снятие рисунка по ttl. Подозрение записывается в базу сразу при обрыве, поэтому перезапуск движка до возвращения DCS его не теряет. Карантин хранится в базе движка, переживает перезапуск движка, виден в sortie status (заметка quarantine в Engine.Health) и снимается владельцем: sortie caps --release <имя> (токен admin) или Engine.ReleaseQuarantine. Если тот же процесс DCS просто переподключился, карантина нет. Операция, которую мост сам отключил после трёх сбоев за 10 минут, тоже QUARANTINED, но только до перезапуска DCS (так её отключает и мост); снять её командой нельзя, и sortie caps --release так и пишет: «still QUARANTINED …: … back after DCS restarts».
  • Типизированные операции на карантине. Карантин message, set_task, spawn_static, draw, menu_tree и других — до снятия владельцем или до другой сборки DCS (обновление DCS снимает его само). Сборка DCS одна на процесс DCS: движок берёт её у связи хуков, а если та её не назвала — у связи миссии. Окружение, в котором нет глобала с версией, сообщает unknown; это слово сборкой не считается, поэтому такая связь карантин не снимает и не мешает ему появиться (какие глобалы есть в каждом окружении настоящего DCS, не измерено). Ту же сборку процесса отдают Engine.Capabilities, Engine.Version и sortie status (unknown там — только пока ни одна связь процесса сборку не назвала). Он действует только на команды ревизии API 1 и новее: в 0.1.0 карантина после падения не было, поэтому команды логики 0.1.0 (ревизия 0) его и не вызывают, и не получают отказа. Пока вид на карантине, реестр ничего не делает в DCS сам: дерево меню не переезжает за слотом и остаётся SUSPENDED, рисунок с истёкшим ttl остаётся зарегистрированным, а запись реестра этого вида (даже такая, что не требует вызова DCS, например дерево для группы без игроков) получает Error::Quarantined.

Карантин функции каталога#

У универсального вызова карантин — по функции DCS, а не по виду операции. Перед каждым вызовом (и внутри пакета) слой Lua записывает его ключ call:<окружение>:<путь> в журнал сбоев моста (Logs/sortie-bridge.journal в Saved Games), и мост успевает записать его на диск до самого вызова. Если DCS упал, мост следующего процесса DCS передаёт движку последний ключ журнала, и на карантин уходит только эта функция: call:mission:land.getHeight становится QUARANTINED, логика получает один CapabilityChanged, а вызов этой функции (один или в пакете) отклоняется с Error::Quarantined, capability() = Some("call:mission:..."), не доходя до DCS. dcs_call, dcs_batch, другие функции каталога и типизированные операции остаются AVAILABLE. Если журнал не назвал вызов (DCS упал до первой записи, файл не удалось записать, мост старше журнала), на карантин уходят все функции пакетов, которые выполнялись; заметка говорит почему. Это касается и пакета, на который DCS уже ответил, если ответ ещё не дошёл до движка: запись журнала «вызова нет» не называет команду, и отличить такой пакет движок не может. Журнал называет и вызов-испытание, который делает сам движок (о нём ниже): если DCS упал внутри него, испытание считается проваленным, а всё остальное, что было в полёте, на карантин не уходит. Три сбоя моста на одной функции за 10 минут (ошибка мимо pcall слоя, паника моста, вызов дольше секунды) тоже отправляют её на карантин, а мост отказывает в ней до перезапуска DCS.

Медленный вызов — не падение. Если все три сбоя — только вызовы дольше секунды (сторожевой таймер моста считает время от записи в журнал до возврата, вместе с упаковкой ответа и чужими обработчиками событий внутри вызова), мост и движок отказывают в этой функции лишь до конца этого процесса DCS: возможность QUARANTINED, заметка говорит Slow, not a crash, в хранилище ничего не записывается. После перезапуска DCS функция снова доступна сама, снимать ничего не нужно. Поэтому тяжёлое чтение (coalition.getGroups, world.getAirbases), для которого испытания нет, не останется на карантине из-за одной медленной минуты на загруженном сервере. Сколько на самом деле занимают самые медленные чтения, ещё не измерено (живая проверка UC-6).

Идентификатор команды может быть любой строкой: длинный или с переводом строки журнал записывает в сокращённом виде с хешем, и вызов такой команды называется журналом так же, как любой другой. Процесс DCS движок отличает по pid и по метке запуска, которую мост создаёт один раз на процесс (Windows выдаёт pid повторно): перезапущенный DCS с тем же pid — это другой процесс, а не обрыв связи. Мост без метки сравнивается только по pid, как раньше.

Ни перезапуск DCS, ни новая сборка DCS, ни перезапуск движка такой карантин не снимают — только владелец: sortie caps --release call:mission:land.getHeight. Исключение — испытание: при следующем старте миссии документированная функция чтения без получателя (land.getHeight, timer.getTime, ...) вызывается один раз с каноническими аргументами каталога; ответ снимает карантин (заметка AVAILABLE об этом говорит), ошибка или повторное падение DCS оставляют его до решения владельца. Для мутаторов, тяжёлых и админских вызовов, методов объектов и функций с пробой испытания нет; заметка называет причину.

Испытание даётся один раз. Движок запоминает, что функция его прошла, и эта запись переживает перезапуск движка. Если та же функция потом снова роняет DCS или мост снова её отключает, она остаётся на карантине уже без испытания, пока владелец его не снимет; заметка говорит no probation: the path faulted again after it passed a probation …. Снятие карантина владельцем стирает и запись (sortie caps --release <имя> стирает её и тогда, когда функция сейчас не на карантине), после этого сбой снова считается первым.

Испытание обходит только карантин своей функции. Оно не отправляется, пока владелец выключил универсальный вызов ([operations] disable = ["dcs_call"]), пока на карантине весь dcs_call, пока мост отключил его или саму функцию до перезапуска DCS, и пока проба показывает, что функции нет в этой сборке DCS. Функция остаётся на карантине, испытание за ней сохраняется (probation waits: … в заметке) и пройдёт при первом старте миссии, когда вызов возможен. Ответ, из которого видно, что DCS вызов не выполнял (мост ответил DISABLED, срок вышел раньше, чем вызов дошёл до DCS), ничего не решает: испытание повторится.

Почему новая сборка не снимает карантин: сервер, который работает без человека, не должен второй раз упасть на том же вызове, пока человек не решил; вызов на карантине вместо этого получает понятную ошибку. Чтобы такой карантин не остался незамеченным после обновления DCS, движок называет его перенесённым: заметка говорит «recorded on DCS <прежняя сборка>, carried over to the running build <текущая>», sortie status (Engine.Health) перечисляет все перенесённые карантины, проба wide_probe — тоже (строки UC-6). Все они снимаются одной командой sortie caps --release-carried-over (Engine.ReleaseQuarantine с carried_over = true, Python — EngineClient.release_carried_over()). Владелец может вернуть правило спецификации: engine.toml [quarantine] clear_calls_on_new_build = true — тогда новая сборка DCS снимает и карантин функции каталога (см. Эксплуатация).

Посмотреть#

sortie caps печатает всё, что не AVAILABLE, с причиной; --all — всю таблицу, --prefix call:mission: — только часть. Python: EngineClient(...).capabilities(prefix).

В тестах FakeDcs: dcs.remove_dcs_function("world.removeJunk") делает сборку DCS без этой функции; со следующей загрузки миссии (dcs.restart()) возможность remove_junk — MISSING_IN_DCS.
