Agent instructions: a Sortie mission repository#

This repository is one DCS World mission built on the Sortie SDK 0.1.0 (https://github.com/lynxr/sortie-sdk, tag v0.1.0). It has two halves:

  • scenario.py: the static mission in Python (sortie-gen over pydcs). It builds the .miz, its manifest and scenario.lock.json, the list of symbols the logic may use.
  • the Rust crate: the mission logic, a separate process that attaches to the Sortie engine sortied running next to DCS. It reads a replica of the DCS world and sends commands.

The SDK is new: its API is not in your training data. Read the matching skill (below) before you change code, and take every name from it or from the SDK source.

Layout#

Cargo.toml, build.rs     the logic crate; build.rs turns scenario.lock.json into typed symbols
src/lib.rs               sortie::include_scenario!(..) and the #[sortie::mission] function
src/main.rs              sortie::main!(<crate>::run);
scenario.py              the scenario; `ident=` makes a symbol for the logic
scenario.lock.json       generated by `scenario.py lock`; committed, never edited by hand
pyproject.toml           uv project with the sortie-gen dependency
dist/                    offline builds (not committed)

Commands#

uv sync                                       # Python environment with sortie-gen
uv run python scenario.py lock                # after adding, renaming or removing an ident
uv run python scenario.py build               # offline build into dist/ (no engine needed)
cargo build --release                         # the logic (build.rs reads scenario.lock.json)
cargo clippy --all-targets -- -D warnings
cargo test                                    # plain unit tests only (see Rules)
uv run python scenario.py lock --check        # CI: fails if the lock is stale

In DCS (the Sortie runtime installed with sortie install, DCS restarted afterwards):

sortied --dev                                 # the engine; no token needed locally
uv run python scenario.py register            # a new build (= a new turn) for the engine
cargo run --release -- --dev                  # the logic; attaches and waits for the mission
uv run python scenario.py watch               # live events; `results` after the session

Rules#

  1. Symbols come from the scenario. A new group, zone, template, flag, airbase or menu for the logic: add it with ident= in scenario.py, run lock, then cargo build. A logic built from another lock is refused by the running mission.
  2. Key commands by step. spawn_group and destroy always get .key("step-name") (they are refused without one under --dev); so does any command a replay must not repeat. A key is stable across runs (a literal or a deterministic counter) and belongs to one command.
  3. The mission function replays. After a restart of the logic process it runs again from the top in the same session. Wait on world state (ctx.wait_until), delay with named timers (ctx.timer), run one-time steps in ctx.once and campaign changes in ctx.once_per_turn.
  4. One thread, short borrows. No blocking calls; background work through ctx.spawn; ctx.world() and StateDoc::get() are dropped before the next .await.
  5. No tests without DCS in SDK 0.1.0. FakeDcs and #[sortie::test] arrive in SDK 0.2 (#[sortie::test] is a compile error until then). Unit-test plain functions with #[test]; test the mission in DCS with sortied --dev.
  6. The .miz comes from scenario.py. Change groups, units and zones there, not in the Mission Editor. A DO SCRIPT added in a @sc.pydcs hook uses sortie_gen.miz.InlineDoScript; a built .miz is never loaded and saved again with pydcs.
  7. Multiplayer slots: a player flight starts at an airfield of its own coalition (player_flight sets the owner; a hook that adds client groups must do it too).
