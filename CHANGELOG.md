# Изменения

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии — по
[SemVer](https://semver.org/lang/ru/). До 1.0 API может меняться между минорными версиями; каждое
такое изменение описано здесь.

## [Unreleased]

## [0.4.0] — 2026-11-25

Ревизия API 3 и ревизия событий 2. Логика ревизий 0, 1 и 2 работает с этим движком; новым
операциям нужен `#[sortie::mission(api_rev = 3)]`, событию `AirbaseOwnerChanged` — ещё и
`event_rev = 2`. Что изменилось в поведении для любой логики и где нужна правка кода — в
«Совместимости». Главное: метки F10 больше не останавливают часы сессии и таймеры; пока в сессии
нет игроков, спавн идёт в темпе моста, а не 2 группы в секунду; время DCS оплачивают два бюджета
писателя (чтения и тяжёлые вызовы), и отказ по лимиту называет лимит и когда повторить. Ещё —
Web API движка, аэродромы и склады второй волны широкого API, задачи и маршрут наземных групп.
Остальное из второй волны (состояние юнитов, обнаружение, слежение Watch, поздняя активация,
правила слотов и другое) — в 0.5.0. В живой DCS ничего из этого ещё не проверялось.

### Добавлено

* Web API: движок отдаёт HTTP/JSON для сайта сервера и сторонних приложений (страница
  [Web API](docs/web-api.md)). Выключен, пока владелец не задаст адрес в `engine.toml`:
  `[http] listen = "127.0.0.1:50780"`, там же `cors_origins`, `max_body_bytes`,
  `actions_per_s`. Чтение из зеркала мира, без DCS и без логики: `GET /api/v1/session`
  (сессия, миссия и сборка, модельное время, пауза, связи, версии), `GET /api/v1/world` (юниты,
  группы, статики, аэродромы; фильтры `coalition` и `category`), `GET /api/v1/world/units/{eid}`,
  `GET /api/v1/players` (игроки и их юниты, без UCID), `GET /api/v1/events` (Server-Sent Events:
  бои, взлёты и посадки, игроки, пауза; id события — `<session>:<seq>`, переподключение с
  `Last-Event-ID` продолжает из журнала движка, а что журнал уже не держит, называет `gap`).
  JSON — собственные стабильные формы (snake_case, коалиция `"red"` / `"blue"` / `"neutral"`,
  точки `{x, y, z}` в метрах DCS), ошибки — `{"error": {"code", "message"}}` с HTTP-статусом.
* Каждый запрос Web API несёт `Authorization: Bearer <токен>` из `tokens.toml`, как gRPC;
  читает любая роль. Токен нужен всегда, и с `sortied --dev` тоже: `--dev` пускает локальные
  программы без токена только в gRPC, потому что по HTTP программу на той же машине не отличить
  от страницы в её браузере или от обратного прокси. Если `[http]` включён, а в `tokens.toml` нет
  ни одного токена, `sortied` предупреждает при старте, что Web API откажет в каждом запросе.
* Роль токена `operator`: читает и вызывает действия логики через Web API, в gRPC — только
  чтение.
* Документы логики для сайта (ревизия API 3, страница
  [Web API](docs/web-api.md#документы-логики)): `ctx.publish("front", &значение)` пишет любое
  `Serialize` в JSON и завершается, когда движок сохранил документ
  (`sortie::publish::Published { rev, updated_unix_ms, changed }`; те же байты ещё раз ничего не
  меняют, `changed == false`), `ctx.unpublish(имя)` убирает документ и отвечает, был ли он. Документ принадлежит логике (её
  имени), а не сессии: он переживает конец сессии, перезапуск логики и движка (лежит в
  `sortie.db`). Движок отдаёт документы сам, не трогая ни логику, ни DCS:
  `GET /api/v1/docs` (список: `logic`, `name`, `rev`, `updated_unix_ms`),
  `GET /api/v1/docs/{logic}/{name}` (JSON как есть, `ETag` — `"<эпоха>-<rev>"`, `304` на
  `If-None-Match`; эпоха — случайная метка базы движка, так что после перезапуска движка без базы
  старый `ETag` не совпадёт с новым содержимым), `GET /api/v1/docs/{logic}/{name}/events`
  (Server-Sent Events: документ сейчас и после каждого изменения, id — `<эпоха>-<rev>`,
  `unpublished`, когда его нет). Правила: имя — 1–64 байта
  `a-z0-9_-`, документ — до 256 КиБ JSON, у логики — до 64 документов; иначе `Error::Invalid`.
  Протокол: `StateOp.publish` (`PublishDoc`), `StateOp.unpublish` (`UnpublishDoc`), ответ
  `StateResult.published` (`PublishedDoc`).
* Действия логики для сайта (ревизия API 3, страница
  [Web API](docs/web-api.md#действия-логики)): `ctx.api().action("send_cap")?` объявляет
  действие и возвращает поток его запросов (`sortie::api::ActionRequests`, `next().await`).
  Сайт или стороннее приложение с токеном роли `operator` (или `admin`) вызывает его
  `POST /api/v1/actions/{logic}/{action}` с JSON в теле; движок передаёт запрос логике по её
  потоку, и её ответ становится ответом: `req.reply(&значение)` — 200 с JSON (до 1 МиБ),
  `req.fail(статус, текст)` — 400–499, `code` `refused`; запрос, брошенный без ответа, SDK
  отвечает 500 `unanswered`. У запроса — `req.json::<T>()`, `req.body()`, имя токена
  `req.token()` и роль `req.role()`. Движок ждёт ответа 10 секунд
  (`sortie::api::ACTION_TIMEOUT`; потом 504 `timeout`), и запрос, который столько пролежал в
  очереди логики, SDK ей уже не отдаёт, а отвечает `unanswered` сам. Движок отвечает 404 на
  действие, которого никто не объявлял, 503 `unavailable`, пока логика не подключена или не
  объявила его в этой сессии, 429 `rate_limited` сверх `[http] actions_per_s` вызовов токена
  (считает сам токен, не имя; с `Retry-After`), 413 сверх `max_body_bytes`, 400 на тело не в
  JSON; `GET /api/v1/actions` — что объявлено сейчас. Каждый вызов пишется в журнал движка (токен, логика, действие, статус,
  время; без тела). Объявления живут, пока жив поток и идёт сессия; после перезапуска логики
  функция миссии объявляет их снова. Правила: имя — 1–64 байта `a-z0-9_-`, до 64 действий, у
  действия один поток; иначе `Error::Invalid`. Протокол: `LogicUp.actions` (`ActionSet`),
  `LogicDown.action` (`ActionCall`), `LogicUp.action_reply` (`ActionReply`, `ActionRefusal`).
* Аэродромы (ревизия API 3, страница [Аэродромы](docs/airbases.md)):
  `ctx.airbase_control([airbases::X, ..]).owner(Coalition::Red).auto_capture(false)
  .radio_silent(true)` меняет у 1–32 аэродромов владельца, автозахват DCS и радиомолчание за
  один кадр DCS (сначала автозахват, потом владелец, потом радио) и читает каждую базу обратно;
  больше баз — несколько команд (`sortie::cmd::MAX_AIRBASES` = 32: около 11 вызовов DCS на
  базу в одном кадре, стоимость ещё не измерена).
  Результат `sortie::cmd::AirbasesControlled { bases }`: по одной `AirbaseControlled { eid, name,
  before, after }` на базу, `before` / `after` — `AirbaseState { owner, auto_capture,
  radio_silent }`, своя ошибка базы — `error()` (`Error::Gone`, `Error::Lua`), остальные базы
  выполняются. Новый владелец сразу в `ctx.world()`, и захват, который DCS подняла раньше
  команды, но движок получил после её ответа, его не откатывает (движок сравнивает их место в
  порядке событий DCS). Движок проверяет весь список до отправки: базы нет в мире, база
  дважды, пустой список или длиннее 32, нечего
  менять — `Error::Invalid` с её именем, в DCS ничего не уходит. Ключ — как у любой меняющей
  команды. Возможность `caps::AIRBASE_CONTROL` включена по умолчанию; живая проверка `AWC-T20`
  (ещё не измерена). FakeDcs: `airbase_auto_capture(имя)`, `airbase_radio_silent(имя)`; сырые
  `Airbase.autoCapture`, `setRadioSilentMode` и их чтения работают с тем же состоянием.
  Протокол: `Command.body.airbase_control = 36` (`AirbaseControl`), `Reply.airbase_control = 11`
  (`AirbasesControlled`, `AirbaseControlResult`, `AirbaseControlState`); операция слоя Lua
  `airbase_control`.
* Событие смены владельца аэродрома (ревизия событий 2, страница
  [Аэродромы](docs/airbases.md#смена-владельца-событие)):
  `ctx.events().of::<v1::AirbaseOwnerChanged>()` — ровно одно событие на каждую смену владельца
  в мире движка, что бы о ней ни сообщило: `cause` — `Captured` (DCS подняла
  `S_EVENT_BASE_CAPTURED`; сразу после её `BaseCaptured`), `Control` (`ctx.airbase_control`;
  раньше ответа команды), `Discovered` (снимок мира после разрыва связи или потери событий
  или запрос состояния нашёл другого владельца). Поля `airbase` (база после смены),
  `previous` (прежний владелец, `Unspecified` — не знал), `owner`. Сообщение о том, что мир
  уже знает, второго события не даёт; захват, который DCS подняла раньше чтения базы, а движок
  получил позже его ответа, тоже (только его `BaseCaptured`); первый снимок сессии ничего не
  публикует. Мир знает нового владельца, когда событие пришло. Владельца, которого другой
  скрипт сменил без события, мир узнаёт только при чтении: логика, которой это нужно,
  опрашивает `ctx.airbases_state(..)`. Фильтры `.airbase(..)`, `.cause(..)`, `.coalition(..)` (новый владелец). То же
  событие — в `GET /api/v1/events` как `airbase_owner_changed`. FakeDcs:
  `capture_airbase(имя, коалиция)` (захват, как его сообщает DCS),
  `set_airbase_coalition_silently(имя, коалиция)` (без события), `lose_events(n)` (движок
  снимает мир заново), `hold_events()` / `release_events()` (события DCS ждут в очереди
  моста, ответы команд уходят сразу). Живая проверка `AWC-T21` (ещё не измерена). Протокол:
  `Event.kind.airbase_owner_changed = 55` (`AirbaseOwnerChanged`, `OwnerChangeCause`),
  `EVENT_KIND_AIRBASE_OWNER_CHANGED = 41`.
* Запросы аэродромов (ревизия API 3, страница
  [Аэродромы](docs/airbases.md#стоянки-полосы-и-состояние-запросы)): стоянки, полосы и
  состояние, ничего не меняют в DCS и не требуют ключа. Одна база —
  `ctx.airbase(sel).parking()` (`.available_only()` — только свободные) -> `Vec<ParkingSpot>`,
  `.runways()` -> `Vec<Runway>`, `.state()` -> `AirbaseState`; много баз одним запросом —
  `ctx.airbases_parking(..)` (до 16), `ctx.airbases_runways(..)` и `ctx.airbases_state(..)` (до
  256) -> `AirbasesRead { bases }`, по одной `AirbaseRead { eid, name, value }` на базу, своя
  ошибка базы — `error()` (`Error::Gone`, `Error::Lua`, `Error::Rejected`), остальные базы
  отвечают. `ParkingSpot { term_index, terminal, point, taken, taken_by, taken_by_name,
  dist_to_runway, to_ac, term_index_0 }`: тип стоянки по имени (`TerminalType`, неизвестное
  число — `TerminalType::Unknown("unknown(<n>)")`), занята ли (нет среди свободных DCS) и кем
  (Eid мира, если DCS назвала объект). `Runway { name, course, length, width, center }`, `course`
  — в радианах, как отдаёт DCS, `heading_deg()` — курс в градусах по документации DCS.
  Владелец, которого DCS прочитала иначе, чем знает мир, сразу в `ctx.world()` и даёт одно
  `AirbaseOwnerChanged` с причиной `Discovered` (если только движок уже не получил захват,
  который DCS подняла после чтения). Слой читает по частям, чтобы большой список не
  останавливал игру: состояние и полосы по 32 базы за кадр, стоянки около 300 за кадр
  (`sortie::cmd::MAX_READ_BASES` = 256 для полос и состояния). Возможности
  `caps::AIRBASE_PARKING`, `caps::AIRBASE_RUNWAYS`, `caps::AIRBASE_STATE` включены по
  умолчанию; живые проверки `AWC-T22`, `AWC-T23`, `AWC-T24` (ещё не измерены). FakeDcs: у
  каждого аэродрома раскладка стоянок и полоса, `take_parking_spot(имя, номер, юнит)` и
  `free_parking_spot(имя, номер)`; сырые `Airbase.getParking` и `getRunways` отдают её же.
  Протокол: `Query.airbase_parking = 5`, `airbase_runways = 6`, `airbase_state = 7`,
  `Reply.airbase_read = 12` (`AirbasesRead`, `AirbaseRead`, `ParkingSpot`, `TerminalType`,
  `Runway`); операции слоя Lua `airbase_parking`, `airbase_runways`, `airbase_state`.
* Запас складов (ревизия API 3, страница [Склады](docs/warehouses.md)): запрос, ничего не
  меняет в DCS и не требует ключа. Один склад — `ctx.warehouse(sel).stock()` ->
  `WarehouseStock { aircraft, weapons, liquids, items }`, много — `ctx.warehouses_stock(..)` (до
  64) -> `WarehousesRead { warehouses }`, по одному `WarehouseRead { warehouse, name, eid,
  value }` на склад в порядке списка, своя ошибка склада — `error()` (`Error::Gone`,
  `Error::Lua`, `Error::Rejected`). Склад — аэродрома, груза-статика или по имени в DCS
  (`WarehouseSel`), каждый не больше одного раза. Без уточнений запрос читает склад целиком
  (`Warehouse.getInventory`, один склад за кадр, большой — копируется по 400 записей за кадр):
  класс самолётов и оружия — `StockClass::Unlimited`
  (DCS, по сообщениям, отдаёт безлимитный класс пустой таблицей) или
  `StockClass::Limited(имя -> количество)`, жидкости — `Liquids::Unlimited` или по
  `Liquid::{JetFuel, AviationGasoline, Mw50, Diesel}` (килограммы предполагаются). `.items([..])`
  (до 64, имя или wsType) и `.liquids()` читают только это (`getItemCount`, `getLiquidAmount`;
  64 вызова DCS за кадр, около 4 из них на поиск склада): `stock.count(предмет)` -> `Amount::Counted(n)` или `Amount::Unlimited`
  (число больше 2^29). Предмет — `sortie::cmd::WarehouseItem`; это тот же тип, что
  `sortie::dcs::WarehouseItem` у сырых обёрток (путь `sortie::dcs::WarehouseItem` остался).
  Возможность `caps::WAREHOUSE_STOCK` включена по умолчанию; живая проверка `AWC-T25` (ещё не
  измерена). Протокол: `Query.warehouse_stock = 8` (`WarehouseStocks`), `Reply.warehouse_stock =
  13` (`WarehousesStock`, `WarehouseStock`, `StockClass`, `StockEntry`, `LiquidStock`,
  `LiquidAmount`, `ItemCount`), в `common.proto` `WarehouseItem`, `WsType`, `Liquid`; операция
  слоя Lua `warehouse_stock`.
* Изменение запаса складов (ревизия API 3, страница
  [Склады](docs/warehouses.md#изменить-запас)): `ctx.warehouse_op()` с `.set(склад, что, n)`,
  `.add(..)`, `.remove(..)` и `.transfer(откуда, куда, что, n)` — до 16 замен одной командой
  (`sortie::cmd::MAX_STOCK_CHANGES`), в одном кадре DCS, всё или ничего. `что` —
  `sortie::cmd::StockItem`: предмет (имя, wsType, `WarehouseItem`; целые до 1 000 000) или
  жидкость (`Liquid`; до 100 000 000). Слой Lua сначала читает каждый счёт и проверяет каждую
  замену с учётом замен перед ней (склад есть, запас не безлимитный, его хватает); не прошла
  хоть одна — ничего не меняется; перед каждым шагом счёт читается снова, и замена, на которой
  DCS упала, которая не сдвинула счёт или чей счёт уже сдвинула замена раньше (один предмет
  назван именем и wsType), откатывает сделанное до неё. Перевод — один шаг: убрано там и добавлено здесь в том же кадре или ничего.
  Убрать больше, чем есть, нельзя (`NotEnough`, до нуля не обрезается). Результат
  `StockChanges { applied, undo_failed, changes }`, по одному `StockChanged { what, outcome,
  message, warehouse, to }` на замену; сторона `StockSide { name, eid, before, after, unlimited }`;
  исход `StockOutcome` (`Done`, `NotApplied`, `Undone`, `UndoFailed`, `Unlimited`, `NotEnough`,
  `Gone`, `DcsError`, `Unchanged`, `Aliased`); `out.failed()` — замены, из-за которых команда не
  применилась. Склад, которого мир не держит живым, перевод на свой же склад, число вне пределов
  — `Error::Invalid` до DCS. В режиме dev (и с `sortied --require-keys`) `.key(..)` нужен каждой
  команде, и из одних `set` тоже: повтор после перезагрузки поставил бы счёт поверх того, что
  успели израсходовать. Возможность
  `caps::WAREHOUSE_OP` включена по умолчанию; живая проверка `AWC-T26` (ещё не измерена).
  Протокол: `Command.body.warehouse_op = 37` (`WarehouseOp`, `StockChange`, `StockTransfer`),
  `Reply.warehouse_op = 14` (`StockChanges`, `StockChanged`, `StockSide`, `StockOutcome`);
  операция слоя Lua `warehouse_op`. FakeDcs выполняет её на том же запасе, что запрос и сырые
  вызовы.
* Имена предметов (ревизия API 3, страница [Склады](docs/warehouses.md#имена-предметов)):
  `ctx.item_names()` — как запущенная DCS называет всё, что знает, и wsType каждого
  (`Warehouse.getResourceMap()`, есть с DCS 2.8.8): оружие — так, как его называют склады
  (`"weapons.missiles.AIM_120C"`), самолёты и техника — по типу. Результат `ItemNames { names,
  unknown, total, skipped, dcs_version, cached, source }`, `names` — `ItemName { name, ws_type }`
  по алфавиту (`ws_type` — `None` там, где DCS даёт `{0, 0, 0, 0}`); `ws_type_of(имя)`,
  `names_of(ws)`, `knows(предмет)`, `get(имя)`, `ItemName::item()`. `.items([..])` (до 64,
  `sortie::cmd::MAX_NAME_LOOKUPS`) — только нужные, остальное — в `unknown`. Движок читает карту
  DCS один раз за процесс DCS и её версию и дальше отвечает из памяти (`cached`), на диск её не
  пишет; таблицы DCS в SDK нет. Запрос ничего не меняет и ключа не принимает (с `.key(..)` —
  `Error::Invalid`: вся карта ушла бы в хранилище движка). Возможность
  `caps::ITEM_NAMES` включена по умолчанию (`MISSING_IN_DCS` в DCS до 2.8.8); живая проверка
  `AWC-T27` (ещё не измерена). Протокол: `Query.item_names = 9` (`ItemNames`),
  `Reply.item_names = 15` (`ItemNameList`, `ItemName`); операция слоя Lua `item_names`. FakeDcs:
  `dcs.set_item_names([(имя, [a, b, c, d]), ..])` — карта (пустая, пока тест её не задал); wsType,
  которому карта даёт одно имя, — запас этого имени в складах FakeDcs; перезагрузка миссии
  карту не сбрасывает. Генератор не изменился:
  `munitions` аэродрома — по wsType (имена знает только запущенная DCS).
* `.of::<T>()` пишет в журнал предупреждение, если тип события новее ревизии событий, которая
  действует (`ctx.event_rev()`): такие события не приходят. Ревизия события —
  `sortie::events::EventType::EVENT_REV`.

* Причина отказа по лимиту данными (ревизия API 3; запрос клиента): `e.limit()` —
  `Option<&sortie::Limit>` (вид `sortie::LimitKind`, имя бюджета вроде `call_rate.read` или
  `dcs_time.read`, чей он, его числа целыми), `e.retry_after()` — когда та же команда, отправленная
  снова без изменений, пройдёт свои бюджеты (из пополнения корзины: после пакета из 256 чтений
  следующий такой же ждёт 1,28 с, одиночное чтение — 0,285 с), `e.is_limit()`,
  `e.is_forbidden()` (запрет: `Rejected` с `capability()` и без лимита; повтор не поможет).
  Лимиты: число вызовов класса, время DCS (`dcs_time.read`, `dcs_time.heavy`), размер пакета и
  запроса, 256 созданных объектов, 1024 дескриптора чтений (дескриптор, который слой отбросил,

  которую мост закрыл после медленных вызовов. `Error::Timeout` с `limit()` — команда не дошла
  до DCS, и лимит называет, чего она ждала (задержка после спавна, тяжёлый слот, кредиты связи,
  `after`, мост не успел начать); без него — ушла в DCS, ответа не было. У остальных отказов
  код ошибки, текст и `capability()` — как в 0.3.0. SDK сам не повторяет; цикл повтора — в
  [вызовах DCS](docs/dcs.md#отказ-по-лимиту).
  Протокол: `CommandError.limit` (`Limit`, `LimitKind`). Python: `CommandFailed.limit`
  (`sortie_gen.errors.Limit`), `retry_after` (секунды), `forbidden`.

### Изменено

* Шаблон проекта: `scenario.py` задаёт `do_scripts="deny"`, так что новая миссия не
  соберётся со своим DO SCRIPT. Пример хука с DO SCRIPT в документации теперь показывает
  сторонний скрипт и `sc.do_scripts = "allow"`.
* Запись владельца в `engine.toml [calls]` с именем на `find` теперь считается чтением, как
  get/is/has: новый путь `find*` может быть `read`, а `heavy` с таким именем включён по
  умолчанию, а не выключен как `mutate`.
* Задачи наземных групп: сырая таблица `Task::raw` теперь для того, чего нет в типизированном
  маршруте (остановка, задачи в точках, маршрут корабля); документация, навыки, AGENTS.md и
  `llms.txt` показывают сначала `Task::ground_route`. `Task::rtb` для наземной группы движок
  отклоняет с текстом «only a ground route or a raw task applies to it» (для морской — по-прежнему
  «only raw tasks apply to it»); подсказки компилятора `Flying` и `TaskFor` называют
  `Task::ground_route(..)`.
* Ошибка компиляции `#[sortie::test]` без FakeDcs больше не обещает тесты в SDK 0.2: FakeDcs
  содержит движок и в публичный SDK пока не входит. Текст: «#[sortie::test] runs the logic
  against FakeDcs, which is not part of the public Sortie SDK yet: it carries the engine.
  Test the mission against a live DCS with `sortied --dev`, and its plain functions with
  `#[test]`.» Так же исправлены документация, навыки, AGENTS.md, `llms.txt` и README.
* Спавн при старте миссии. Пока в сессии никого нет (связь hooks не видит ни одного игрока, и ни
  у одного юнита нет игрока), спавны идут через ворота разогрева: по умолчанию 200 групп и
  4000 юнитов в секунду, то есть их ограничивает бюджет моста в DCS, а не 2 группы в секунду.
  Пока мост оценивает спавн дороже доли команд в pump (так до первых замеров: оценка 1500 мкс,
  доля по умолчанию не больше 900 мкс), идёт один спавн за pump: 50 в секунду при 50 fps и
  выше, 30 при 30 fps, 20 при 20 fps; спавн, который мост замерил дешёвым, идёт по несколько за
  pump. Как только игрок подключился, занял слот или летит в одиночной игре, действуют обычные
  ворота (2 группы и 24 юнита в секунду). Без связи hooks разогрева нет. Игроки — клиенты того процесса DCS, чья
  связь hooks о них сообщила: DCS, упавшая или убитая при клиентах на сервере, об их уходе не
  сообщает, поэтому новый процесс DCS начинает без игроков, и разогрев снова действует (а не
  только после перезапуска движка). Настройки — `engine.toml spawn_gate =
  { warmup_groups_per_s, warmup_units_per_s }` рядом с прежними; равные значения выключают
  разогрев. Для логики меняется только время: спавны в пустой сессии приходят быстрее.
* Мост допускает спавн в ближайший pump: первая команда `BULK` за pump выполняется, даже если её
  оценка (1500 мкс до замеров) больше доли команд, пока осталось не меньше половины этой доли.
  Раньше спавн ждал 250 мс и pump без других команд, то есть шёл не чаще 4 раз в секунду. Запрос
  (`QUERY`), который ждёт 250 мс, идёт раньше спавнов, так что поток спавнов не держит снимок
  мира. Оценку стоимости вызова каталога DCS мост ведёт отдельно по каждому пути: один медленный
  вызов (`land.findPathOnRoads` клиента на 2241 мс) больше не делает дорогими все остальные
  вызовы, и они снова идут несколько за кадр. Медленные вызовы мост считает отдельно от сбоев
  (`bridge.status().slow_calls`).
* Владелец задаёт бюджет моста в `engine.toml [bridge]`: `pump_budget_us` (по умолчанию 1500),
  `hooks_budget_us` (500), `min_budget_us` (200), `max_events_per_frame` (256), `heartbeat_ms`
  (1000) и `sample_rates` (`players`, `air_ai`, `ground_moving`, `ground_static`, `ships`, Гц).
  Значение вне границ останавливает `sortied` при старте. Документация называла бюджет pump
  1000 мкс; по умолчанию он 1500.
* Выборка позиций в DCS больше не просматривает всех юнитов каждый pump. Раньше, когда читать
  было почти некого, слой Lua 50 раз в секунду проходил каждого отслеживаемого юнита (при 5000
  юнитах — 5000 записей за pump). Теперь у каждого класса своя очередь в порядке последних
  чтений, и pump смотрит только на голову каждой из пяти очередей и на то, что читает. Игроки
  читаются первыми, остальные — кто дольше ждёт. Чтение юнита — один `pcall` вместо восьми,
  массив пачки один на все pump. Движок и логика получают то же, что раньше. Нужен новый слой
  Lua: `sortie install` и перезапуск миссии.
* Снимок мира (при старте миссии, до которого логика ждёт, и после потери событий) больше не
  читает в одном pump 50 групп без оглядки на время. Порция кончается между объектами, когда
  вышло время, которое мост даёт шагу (десятая доля бюджета pump и то, что команды оставили от
  своей: около 1 мс при 50 fps без команд, около 0,3 мс при 20 fps), или набралось 100 юнитов;
  первая группа порции идёт целиком. Мир, который получает логика, тот же; большой мир на
  низком FPS читается дольше, но без фриза. `getDesc` слой зовёт один раз на тип юнита, а не
  для каждого (рождение юнита звало его дважды), и выборка берёт класс родившегося юнита из
  копии события: рождение юнита — 12 вызовов DCS вместо 16. Нужен новый слой Lua:
  `sortie install` и перезапуск миссии; со старой DLL моста (DCS ещё не перезапущена) порцию
  ограничивают 100 юнитов.

* Пакет `DcsBatch` с вызовом `mutate` теперь оплачивает своё время DCS бюджетом чтений
  `dcs_time.read` и отклоняется, пока он исчерпан, как пакет чтений (раньше такой пакет время
  DCS не оплачивал вовсе); его вызовы `mutate` по-прежнему считаются и в лимите 50 в секунду.
  Отдельный вызов `mutate` время DCS не оплачивает, как раньше.
* Проверка `span_300km` (концы не дальше 300 км друг от друга по карте, иначе `Error::Invalid`
  до DCS) теперь стоит и на `land().path_on_roads(..)`, и на `land().road_path(..)`. Запись
  каталога называет точки, которые лежат в простых числах, новым полем `points` (пары имён
  аргументов: север, восток); владелец может задать его в своей записи `engine.toml [calls]`,
  а у встроенной записи — нет. Справочник каталога, обёртки Rust и Python называют проверку и
  точки, которые она меряет.
* Документация ошибок: `Error::Timeout` теперь описан как два случая (не дошла до DCS / ушла,
  а ответа нет), задержка после спавна — для `set_task`, `push_task` и `set_option` группы
  любого вида, ключ, под которым уже была другая команда, — `Error::Invalid`, и совет не
  завершать функцию миссии одной необязательной командой (повтор с тем же ключом, запись
  ошибки). Подсказки `Error::Timeout` и `Error::Rejected` (`e.help()`) говорят то же.
* Документация объектов: что DCS знает о местности — ни леса и деревьев, ни объёма скал и
  моделей скрипту не видно; что делать вместо этого (сетка высот, поиск объектов вокруг,
  проверенные площадки зонами сценария). Комментарий `OBJECT_CATEGORY_SCENERY` больше не
  обещает деревьев; у `land().surface_type(..)` в каталоге заметка: значения «лес» нет, лес —
  `LAND`.
* `.at(точка, курс)` у `ctx.spawn_group(..)` работает как раньше, но документация теперь
  говорит, что он делает: первая машина — в точке, остальные — со смещениями из шаблона без
  поворота, **у всех машин один курс**, маршрут шаблона заменяет одна точка маршрута (раньше
  doc-комментарий говорил, что маршрут шаблона «сдвигается»; так не было никогда).
* Справочник каталога DCS и страницы складов и вызовов DCS говорят, где читать карту имён
  предметов DCS (`Warehouse.getResourceMap`): в типизированном `ctx.item_names()`, записи в
  каталоге у этой функции нет. Им и проверяют предметы кампании до наполнения склада.
* Тяжёлые вызовы логики идут по одному: следующий тяжёлый вызов, отправленный, пока предыдущий
  ещё не вернулся (ждёт тяжёлого слота, выполняется или ждёт позднего ответа после
  `Error::Timeout`), отклоняется сразу — `Error::Rejected`, `limit()` — `DcsTime`
  `dcs_time.heavy`, `retry_after()` — `None`: сколько ждать, станет ясно, когда придёт ответ
  предыдущего и движок спишет его время. Раньше такой вызов принимался на полный бюджет и шёл
  сразу за первым: два пути по дорогам по 2,2 с подряд останавливали DCS на 4,5 с. Отправляйте
  следующий тяжёлый вызов после ответа предыдущего. ([Время DCS](docs/dcs.md#время-dcs).)
* Документация ожиданий: команда с `.after(a)`, у которой `a` упала, получает код и
  `capability()` команды `a` и `limit()` вида `After` (`wait.after`): это не обязательно
  `Error::Timeout` (у отклонённой `a` — `Error::Rejected`), `is_forbidden()` — `false`,
  `retry_after()` — `None`, и та же команда, отправленная снова, сразу упадёт так же. Раньше
  документация говорила, что любое ожидание кончается `Error::Timeout`, а повтор безопасен.

### Устарело

* Обёртки каталога `ctx.dcs().airbase(..).set_coalition(..)`, `.auto_capture(..)` и
  `.set_radio_silent_mode(..)` помечены `#[deprecated]` в пользу `ctx.airbase_control(..)`
  (`superseded_by = "airbase_control"` в каталоге и в возможностях `call:mission:Airbase.*`).
  Они работают как раньше; чтения (`coalition()`, `auto_capture_is_on()`,
  `radio_silent_mode()`) не устарели.
* Обёртки каталога `ctx.dcs().warehouse(..).set_item(..)`, `.add_item(..)`, `.remove_item(..)`,
  `.set_liquid_amount(..)`, `.add_liquid(..)` и `.remove_liquid(..)` помечены `#[deprecated]` в
  пользу `ctx.warehouse_op()` (`superseded_by = "warehouse_op"`). Они работают как раньше;
  чтения (`inventory(..)`, `item_count(..)`, `liquid_amount(..)`) не устарели.

### Исправлено

* Часы сессии. В миссии, которая начинается не в полночь, первая же метка F10 (панель логики,
  `MarkCommand` или метка игрока) останавливала часы движка: DCS кладёт в поле `time` событий
  `S_EVENT_MARK_*` время суток (по вики Hoggit — `timer.getAbsTime`, секунды от полуночи первого
  дня миссии), а движок двигал часы по времени любого события и назад их не ведёт. В миссии с
  09:00 часы вставали около 32 400 с: `Tick.model_time` и `ctx.model_time()` замирали,
  `ctx.sleep` и `ctx.timer` не срабатывали, дедлайн именованного таймера сохранялся во времени
  суток, `model_time` результатов команд стоял, а задача группе сразу после спавна кончалась
  `DEADLINE` («tasking delay after spawn»). Теперь часы движка идут только по модельному
  времени DCS (pump миссии в heartbeat, выборки, снимки мира); время события двигает их, только
  если оно не дальше 5 с впереди последнего такого отчёта. Время дальше часы не двигает,
  пишется в лог движка раз на вид события и считается в `Engine.Health` (новое поле
  `LinkHealth.event_times_ignored`, `sortie status` показывает его, когда оно не 0). Слой Lua
  0.4.0 переводит время метки в модельное в момент события и хранит значение DCS в новом поле
  `Mark.dcs_time` (ревизия API 3). Что меняется для логики SDK 0.1.0–0.3.0: `model_time`
  события `Mark` теперь модельное время, а не время суток (с новым слоем Lua: `sortie install`
  и перезапуск миссии), а тики, результаты команд и дедлайны таймеров после метки снова идут
  модельным временем; поле `dcs_time` ей не отправляется, остальное — байт в байт как было.
  Что DCS кладёт в `time` метки на самом деле, измерит новый шаг пробы `EVT-L18`.
* `Missions.GetResults` сразу после того, как `ctx.end_session(..)` завершился, иногда отвечал
  «no results for session»: движок отвечал логике раньше, чем записывал итоги. Теперь итоги
  записаны до ответа; логика по-прежнему получает ответ на `EndSession` раньше, чем конец
  сессии.
* Ожидание у ворот спавна съедало срок команды. Из 100 `spawn_group`, отправленных разом,
  около 38 последних кончались `Error::Timeout` («spawn rate limit»): при 2 группах в секунду
  очередь идёт 50 с, а срок полосы BULK — 30 с. Теперь время, которое команда ждёт ворота спавна
  (и место среди 16 спавнов, на которые DCS ещё не ответила), в срок не идёт: все 100 выполнятся.
  То же для пакета `spawn_batch` (два пакета сразу теперь получают места по очереди; раньше
  второй ждал, пока первый не кончится, и мог не успеть в срок) и для задержки задач после
  спавна: `set_task` или `set_option` группе, чей спавн ещё стоит в очереди, ждёт его, не
  расходуя свой срок, и уходит в DCS после спавна и 0,5 с (отчёт клиента:
  `set_option(Alarm::Red)` сразу после спавна). Срок по-прежнему идёт, пока команда ждёт связь,
  кредиты или `after`, пока спавн, которого ждёт задача, потерян или ответил `Timeout`, и пока
  пакет ждёт ответа DCS на свои же элементы, занявшие все 16 мест: если DCS замолчала, пакет
  кончается `Timeout`, и спавны и задачи за ним идут дальше, а не ждут вечно.
* Позиции замирали во время полного обхода. Раз в 30 с слой Lua читает всех юнитов, чтобы
  найти тех, о чьей гибели DCS не сообщила, и пока обход шёл (при 5000 юнитах — больше секунды),
  обычные чтения стояли: позиции игроков в мире логики не менялись. Теперь обход берёт четверть
  квоты выборки, остальное идёт обычным чтениям, и игроки сохраняют свои 5 Гц. Игрок, севший в
  уже существующий юнит, теперь опрашивается с частотой игрока (раньше — с частотой класса,
  который юнит имел при появлении), вышедший — снова с частотой ИИ. Новые `sample_rates` (их
  мост получает, когда движок перезапущен с другим `[bridge]`) действуют сразу: юнит класса,
  у которого частота была 0, раньше ждал следующего обхода. Нужен новый слой Lua:
  `sortie install` и перезапуск миссии.
* Снимок мира больше не обрывается через 60 с, пока порции идут: срок считается от последней
  порции. Раньше снимок большого мира, который не успел за 60 с, кончался `TIMEOUT`, и сессия
  шла на мире без последних порций (заметка «the world snapshot failed»).
* Один медленный тяжёлый вызов больше не закрывает логике чтения на минуты (отчёт клиента:
  `land.findPathOnRoads` за 2241 мс, после которого ни одно назначение маршрута не прошло).
  Тяжёлый вызов оплачивал время DCS бюджетом чтений писателя (20 мс в секунду) без нижней
  границы, и `timer.getTime`, `Controller.hasTask` и остальные чтения той логики отклонялись
  около 111 с. Теперь у тяжёлых вызовов свой бюджет `dcs_time.heavy`: 20 мс в секунду, не больше
  200 мс сразу, долг хранится целиком — после вызова длиной `C` мс следующий тяжёлый вызов ждёт
  около `(C − 200) / 20` с (после 2241 мс — 102 с, текст отказа называет бюджет и сколько ждать),
  а чтения идут сразу. Одиночное чтение видит долг бюджета чтений `dcs_time.read` не глубже
  20 мс: чтение или пакет, которые заняли больше, закрывают одиночные чтения не больше чем на
  секунду. Пакет видит долг целиком: следующий пакет ждёт, пока долг не выплачен, так что
  пакетами бюджет не обойти (пакет из 256 чтений за 770 мс раз в секунду держал бы DCS около
  60 % времени кадра; теперь следующий такой пакет ждёт 37,5 с). Текст отказа по бюджету чтений
  не изменился. ([Время DCS](docs/dcs.md#время-dcs).)
* Вызов, на который движок ответил `Error::Timeout`, а DCS его всё же выполнила, теперь
  оплачивает своё время, когда приходит поздний ответ (раньше — ничего).
* Долг писателя переживает перезапуск логики под тем же токеном или именем, как и раньше, но
  движок больше не держит писателей вечно: через 10 минут тишины он забывает того, чьи бюджеты
  снова полны (долг так не прощается).

### Совместимость

* Нужны новые `sortied`, мост и слой Lua: `sortie install` и перезапуск DCS (DLL моста DCS
  загружает при старте). Что из нового требует слоя Lua 0.4.0 и что отвечает старый слой,
  сказано в пунктах ниже и в «Изменено».
* Документы и действия — операции ревизии API 3: логика объявляет
  `#[sortie::mission(api_rev = 3)]` (иначе `Error::Revision`), движок 0.3.x отвечает
  `Error::EngineTooOld`; в обоих случаях ничего не отправлено. `Engine.Version`,
  `Start.api_rev` и `Engine.Capabilities` теперь говорят `api_rev = 3`. Логика ревизий 0, 1 и 2
  продолжает работать; что меняется для неё, сказано в пунктах ниже.
* `ctx.airbase_control` — тоже ревизия API 3, с тем же правилом. Слою Lua 0.3.x нужен
  `sortie install`, иначе `airbase_control` — `NOT_IMPLEMENTED`.
* Запросы аэродромов (`ctx.airbase(..)`, `ctx.airbases_parking/runways/state(..)`) — тоже
  ревизия API 3 и тоже требуют нового слоя Lua (`sortie install`), иначе `airbase_parking`,
  `airbase_runways`, `airbase_state` — `NOT_IMPLEMENTED`.
* Запрос склада (`ctx.warehouse(..)`, `ctx.warehouses_stock(..)`) — тоже ревизия API 3 и тоже
  требует нового слоя Lua, иначе `warehouse_stock` — `NOT_IMPLEMENTED`.
* `ctx.warehouse_op()` — тоже ревизия API 3 и тоже требует нового слоя Lua, иначе
  `warehouse_op` — `NOT_IMPLEMENTED`.
* `ctx.item_names()` — тоже ревизия API 3 и тоже требует нового слоя Lua, иначе `item_names` —
  `NOT_IMPLEMENTED`.
* `set_task` и `push_task` наземной или морской группы — не новая операция: ревизия не нужна,
  движок и слой Lua любой версии принимают сырую задачу для любой группы. Нужен только новый
  SDK. Код, который отдавал задачи самолётам, компилируется как раньше, кроме двух случаев:
  свой тип с `Into<Task>` и обобщённый аргумент `impl Into<Task>` (или `T: Into<Task>`), который
  код передаёт дальше в `push_task` / `set_task`: трейт `TaskFor` закрыт. В обоих случаях
  помогает `.into()` до `Task`: `g.push_task(task.into())`.
* `Task::ground_route(..)` — ревизия API 3: логика объявляет `#[sortie::mission(api_rev = 3)]`,
  иначе `Error::Revision`; с движком 0.3.x — `Error::EngineTooOld`; в обоих случаях ничего не
  отправлено. Слой Lua 0.3.x принимает такую задачу, но точку старта не уточняет (`lead_start`
  он не знает): колонна стартует из позиции, которую видел движок (у едущей группы — до 2 с
  назад); `sortie install` ставит новый слой. Сырые задачи уходят в DCS ровно как раньше.
* У `Task` новый вариант `Task::GroundRoute`: `match` по `Task` без ветки `_` его не
  скомпилирует.
* `land().path_on_roads(..)` — запись каталога ревизии API 3 (первая выше ревизии 1): логика
  объявляет `#[sortie::mission(api_rev = 3)]`, иначе `Error::Revision`; с движком 0.3.x —
  `Error::EngineTooOld`. Слой Lua не менялся: вызов идёт через `dcs_call`. Вызов по пути
  (`dcs-raw`, Python) к движку 0.3.x отвечает `Error::Rejected`: его каталог этой записи не знает.
* `land().road_path(..)` — тоже ревизия API 3 с теми же правилами, и ей нужен слой Lua 0.4.0
  (`sortie install`): слой 0.3.x не знает функций `sortie.*` и отвечает `MISSING`
  (`Error::Unavailable`). Владелец движка может выключить её в `engine.toml` или сузить
  `max_points`, но своих записей `sortie.*` добавить не может: движок с такой записью не
  стартует (у слоя таких функций нет).
* Сборка сценария, в который хук добавил Lua (DO SCRIPT, DO SCRIPT FILE, скрипт инициализации,
  условие LUA PREDICATE), теперь предупреждает (по умолчанию `do_scripts="warn"`); сборка без
  своего Lua не меняется ни в одном байте.
* FakeDcs: `timer.getAbsTime` и `timer.getTime0` берут время суток старта из `start_time`
  манифеста (как оно записано; без него — полдень, как раньше всегда), `set_start_time_of_day`
  задаёт его в тесте. События меток F10 приходят от FakeDcs так, как по вики их даёт DCS и
  переводит слой Lua 0.4.0; `layer_before_0_4(true)` играет старый слой.
* FakeDcs: склад, которого тест не задал, теперь безлимитный во всех классах, как аэродром
  миссии без `munitions` (раньше он считал каждый предмет с нуля, а `getInventory` отдавал
  самолёты и жидкости пустыми): сырой `getItemCount` там отвечает `FAKE_UNLIMITED_COUNT`
  (2^30), а `set_item`, `add_item`, `remove_item` ничего не меняют. Тест, которому нужен
  счёт, задаёт запас: `dcs.set_warehouse_stock(имя, FakeStock::unlimited().weapons([..]))`.
  `dcs.warehouse_count(имя, предмет)` отвечает то, что ответил бы `getItemCount`.
* Ревизия событий движка теперь 2 (`Engine.Capabilities`, `Start.event_rev` логики, объявившей
  2): `AirbaseOwnerChanged` получает только логика с
  `#[sortie::mission(api_rev = 3, event_rev = 2)]`; логика и подписчик `Events.Subscribe`
  ревизий событий 0 и 1 его не видят, а `BaseCaptured` приходит всем как раньше. Номера `seq`
  у них пропускают такие события (как и события ревизии 1 у логики ревизии 0): это не потеря.
  Движок 0.3.x событий ревизии 2 не знает: `ctx.event_rev()` там 1.
* Ревизия событий 2 — часть ревизии API 3: `#[sortie::mission(api_rev = 2, event_rev = 2)]`
  теперь ошибка компиляции. Логике SDK 0.3.0 с таким объявлением (оно компилировалось) движок
  не отказывает, а отдаёт ревизию событий 1, как отдавал движок 0.3.0, и событий, которых её SDK
  не знает, она не получает; то же для подписчика `Events.Subscribe` с `api_rev = 2`.
* `CommandError.limit` — поле ответа: движок 0.4.0 заполняет его для любой логики, SDK до 0.4.0
  его не читает и видит тот же код, текст и `capability`, что от движка 0.3.0. Против движка
  0.3.0 `e.limit()` и `e.retry_after()` — `None`. У `sortie::Failure` новое публичное поле
  `limit`: код, который строит `Failure` литералом без `..Default::default()`, его добавляет.
  `Limit` и `LimitKind` — `#[non_exhaustive]`.
* Пределы дескрипторов (`handles.created`, `handles.read`) называет слой Lua 0.4.0: со слоем
  0.3.x (без `sortie install`) их отказы приходят без `limit()`, как раньше (предел созданных
  объектов — с `capability`).
* `.at_formation(..)` — ревизия API 3: логика объявляет `#[sortie::mission(api_rev = 3)]`,
  иначе `Error::Revision`; с движком 0.3.x — `Error::EngineTooOld`; в обоих случаях ничего не
  отправлено. `.at(..)` отправляет те же байты, что в 0.3.0, поэтому ключ старого спавна
  остаётся тем же. Тот же ключ у `.at`, а потом у `.at_formation` — другая команда:
  `Error::Invalid`; переходя на `.at_formation`, дайте спавну новый ключ. Слой Lua не менялся.
  Манифест с `Template.heading_rad` читают и движок, и SDK 0.4.0; JSON-манифест с этим полем SDK
  0.3.x не прочтёт (неизвестное поле), `.pb` — прочтёт. Пересобранные генератором манифесты
  получают новое поле (у примеров — новый build id и digest).
* Таблицы перечислений в каталоге проверяются строже при загрузке: `engine.toml` с записью
  `enum:env.<..>` (или другой таблицей данных: `net`, `DCS`, `timer`, `Warehouse` …), с таблицей
  из 7 имён или с таблицей DCS в записи среды `hooks` останавливает `sortied` при старте с
  правилом в сообщении; 0.3.0 такую запись загружал, а каждый её вызов отклонял слой Lua. Ключ
  перечисления из такой таблицы отклоняется с тем же правилом, а не с «no enum table».
* Число в аргументе `enum:<таблица>` — новое для 0.4.0: движок 0.3.x отвечает
  `Error::Invalid`, слой Lua 0.3.x — тоже (`Error::Invalid`, число до DCS не доходит), нужен
  `sortie install`. Ключи работают с любым слоем.
* Движок 0.4.0 отклоняет второй тяжёлый вызов писателя, пока первый не вернулся, для логики
  любой ревизии: логика, которая отправляла два тяжёлых вызова сразу (например, два
  `world.getAirbases` в `join!`), получит `Error::Rejected` на одном из них, где движок 0.3.0
  ставил второй в очередь. После пакета, который занял больше 20 мс времени DCS, следующий
  пакет того же писателя ждёт весь долг, а не секунду, как одиночное чтение.
* Остальные изменения бюджетов времени DCS тоже действуют для логики любой ревизии: тяжёлый
  вызов оплачивает своё время бюджетом `dcs_time.heavy`, а не бюджетом чтений, так что после
  долгого тяжёлого вызова ждёт следующий тяжёлый вызов, а чтения идут сразу; одиночное чтение
  видит долг бюджета чтений не глубже 20 мс; пакет с вызовом `mutate` оплачивает
  `dcs_time.read` и отклоняется, пока бюджет исчерпан; вызов, на который движок ответил
  `Error::Timeout`, оплачивает время, когда приходит его поздний ответ. Текст отказа по бюджету
  чтений прежний. ([Время DCS](docs/dcs.md#время-dcs).)
* Время события `Mark` у логики любой ревизии — модельное, а не время суток, когда в DCS стоит
  слой Lua 0.4.0; значение DCS получает только логика ревизии API 3 (`Mark.dcs_time`). Часы
  движка после метки идут правильно и со старым слоем («Исправлено», часы сессии).
* Спавн в пустой сессии быстрее (ворота разогрева, «Изменено»), и логика это видит только по
  времени. Разогрев выключают равные значения `warmup_groups_per_s` и `groups_per_s`,
  `warmup_units_per_s` и `units_per_s` в `engine.toml spawn_gate`. Файл 0.3.x, который поднял
  обычные ворота выше 200 групп и 4000 юнитов в секунду, загружается: разогрев тогда не ниже
  них. FakeDcs начинает как сервер, на который никто не зашёл, поэтому спавны в тестах идут
  через ворота разогрева; игрок (`dcs.connect_player(..)` или юнит с игроком) включает обычные.
* Запись владельца `heavy` в `engine.toml [calls]` с именем на `find` теперь включена по
  умолчанию (раньше она считалась изменяющей и была выключена, пока её не включат). Если она не
  должна работать, выключите её (`enabled = false` у записи или путь в списке `[calls]
  disable`).
* Устаревшие обёртки (раздел «Устарело») дают предупреждение компилятора `deprecated`: сборка с
  `-D warnings` на них остановится, пока код не перейдёт на `ctx.airbase_control(..)` и
  `ctx.warehouse_op()`.

## [0.2.0] — 2026-11-17

Основа широкого API (волна 1, ревизия API 1). Логика 0.1.0 работает без изменений.

### Добавлено

* Общий словарь в `sortie.v1` (`common.proto`): селекторы `ObjSel`, `AirbaseSel`, `PlayerSel`,
  `WarehouseSel`, `ZoneSel`, `ControllerSel`, `Audience`, место `Anchor`, области `MapArea` и

  `GroupRef`, `AirbaseRef`, `ZoneRef`, `Vec3`, `MapPoint`, `Coalition`).
* Типизированный ответ команды: `CommandResult.reply` (снимки созданного и удалённого),
  `world_rev` (ревизия мира с эффектом команды) и `replayed` (ответ на повтор по ключу).
  SDK кладёт снимки ответа в реплику сразу: после `spawn_group(..).await?` группа видна в
  `ctx.world()` до следующего тика.
* Ревизии объявляет логика: `#[sortie::mission(api_rev = 1, event_rev = 0)]` (по умолчанию 0 и
  0 — поведение 0.1.0). `ctx.engine_api_rev()`, `ctx.event_rev()`, `ctx.writer()` говорят, что
  ответил движок. Операция новее объявленной ревизии — `Error::Revision`, новее движка —
  `Error::EngineTooOld`; в обоих случаях ничего не отправлено.
* `Engine.Version` отдаёт `api_rev`.
* Вызовы DCS (ревизия API 1): каталог DCS API `catalog/dcs_api.toml` и типизированные обёртки
  из него — `ctx.dcs().land().surface_type(p)`, `ctx.dcs().airbase(a).set_coalition(c)`,
  `ctx.dcs().warehouse(w).add_item(..)`, лазерные пятна, звуки из `.miz`, чтения хуков `net.*`
  (страница [Вызовы DCS](docs/dcs.md), список — [справочник каталога](docs/dcs-catalog.md)).
  Движок проверяет каждый вызов по каталогу до DCS; изменяющие функции выключены, пока владелец
  движка не включит их в `<Saved Games>/Sortie/engine.toml` (`[calls]`) или не запустит
  `sortied --dev`. Чтение не берёт ключ. Команды `DcsCall` и `DcsBatch`, ответ `Reply.call` /
  `Reply.batch`. Вызов по строке пути и пакеты — за cargo-фичей `dcs-raw`. В Python — модуль
  `sortie_gen.dcs_api` поверх `EngineClient.dcs_call`. Метод объекта выполняется через таблицу
  класса самого объекта, как `unit:getCoalition()`: класс `CoalitionObject` есть только в
  документации DCS, в игре такой таблицы нет, поэтому `coalition()` и `country()` работают у
  юнита, статика, аэродрома и оружия. `land().profile(a, b)` берёт два `Vec3` (DCS читает у
  них `x` и `z`). Число, которое DCS вернул строкой (id объекта в 2.9.31), приходит числом:
  `static_object(..).id()`, `airbase(..).id()`, `group(..).id()`.
  `static_object(..).cargo_display_name()`, как и `cargo_weight()`, движок выполняет только
  для груза (`Error::Invalid` для другого статика: по описанию DCS на нём падает).
  Повтор вызова с ключом возвращает сохранённый результат вместе с объектами и дескрипторами:
  `spots().create_laser(..).key("lase-1")` после перезапуска логики в той же сессии отдаёт тот
  же `Handle` (раньше повтор заканчивался `Error::Invalid`, и пятно нельзя было убрать до
  конца сессии). Состояние объектов в ответе на повтор читается из мира заново. Под ключом не
  хранятся только значения результата больше 64 КиБ: повтор такого вызова — новая ошибка
  `Error::ResultNotKept` (`sortie::result_not_kept`), в Python — `errors.ResultNotKept`.
  Аргумент-объект, его id или имя проверяется на класс параметра и тогда, когда он задан
  дескриптором или результатом предыдущего вызова пакета: `Spot.createLaser` с пятном вместо
  источника или id юнита там, где нужен id группы, — `Error::Invalid`, DCS не вызывается
  (раньше такой вызов уходил в DCS). Таблица в результате приходит целиком или значением
  `Value::Cut(n)` с `truncated`; ответ одной команды, все вызовы пакета вместе, — не больше
  150 000 значений (раньше большой пакет чтений терял все результаты с ошибкой
  `sortie::bridge_fault` «does not decode»).
* Объекты (ревизия API 1, страница [Объекты](docs/objects.md)): `ctx.spawn_static(тип, страна)`
  — статик, груз или рабочий FARP (`.heliport(..)`), с политикой имени `.on_conflict(..)`
  (`Fail`, `Keep`, `Replace`); категорию и модель DCS движок берёт из таблицы типов
  `catalog/static_types.toml` (её генерирует sortie-gen из базы pydcs). Статик сразу в мире,
  событие `Birth` с `synthesised = true`. `ctx.destroy(obj)` уничтожает любой юнит, статик или
  груз; юнит с игроком — только с `.allow_player()` (так же `group.destroy()` при ревизии 1).
  `ctx.remove_junk(объёмы)` убирает обломки и воронки. Протокол: `SpawnStatic`,
  `Destroy.object` / `allow_player`, `RemoveJunk`, `Reply.junk`, `Birth.synthesised`,
  `GONE_REASON_REPLACED`. Обёртки `object(..).destroy()` и `world().remove_junk(..)` каталога
  помечены устаревшими в пользу этих операций. `Keep` для FARP возвращает и его аэродром
  (`SpawnedStatic::airbase`), как при постановке. После `destroy()` статика или груза слой
  Lua в следующих кадрах DCS (не дольше десяти) смотрит, исчез ли объект: по сообщениям, DCS не убирает FARP
  (не измерено). Если объект остался, `ctx.destroy(..)` и `Replace` отвечают `Error::Lua`
  («DCS did not remove …»), мир считает статик и его аэродром живыми, второй FARP поверх
  первого не ставится. Ответ на уничтожение статика приходит, когда объект исчез (обычно на кадр позже); юниты,
  группы и оружие — как раньше. В FakeDcs — `dcs.survives_destroy(имя, true)`. Юнит с категорией
  `Structure` (вооружённое строение в наземной группе) адресуется по Eid как юнит:
  раньше `ctx.destroy(eid)`, якорь и получатель вызова отвечали `Error::Gone`, а `UnitSel` —

* Пакет спавнов (ревизия API 1, страница [Объекты](docs/objects.md#пакет-спавнов)):

  имени элементы помечены `settled`, ни один не ставится дважды. Протокол: `SpawnBatch`
  (`Command.body.spawn_batch = 35`), `SpawnItem`, `SpawnResult`, `Reply.spawns`; возможность
  `spawn_batch`.
* Реестр ресурсов и рисунки на карте (ревизия API 1): `ctx.map()` — метки с текстом, линии,

  `ctx.world().resources()`), событие `ResourceEnded` (ревизия событий 1), у событий `Mark`

* Деревья меню F10 (ревизия API 1, страница [Деревья меню F10](docs/menus.md)):
  `ctx.menus().tree(имя)` — пункты и подменю для всех, коалиции или одной группы, по имени.
  Повтор того же дерева не идёт в DCS, при изменении движок убирает и добавляет только
  изменённые пункты. Меню группы следует за слотом: пока в группе нет игрока, дерево
  приостановлено (`SUSPENDED`), движок ставит его, когда игрок занял слот, убирает, когда слот
  опустел, и ставит заново для нового id группы (динамические слоты). Двух пунктов с одной
  надписью на уровне быть не может. Нажатие несёт дерево, `id` пункта и его `arg`
  (`MenuPressed.tree`, `item`, `arg`, ревизия событий 1). Протокол: `MenuTree`, `MenuNode`,
  `MenuOverflow`, `ResourcePut.spec.menu_tree`.
* Страницы меню (`MENU_OVERFLOW_PAGE`, по умолчанию): уровень дерева длиннее 10 пунктов DCS
  показывает как 9 пунктов и подменю `More...` с остальными, и так дальше. Страница
  корневого уровня дерева называется `More... (<имя дерева>)`: этот уровень дерево делит с
  другими деревьями и командами меню из сценария, а DCS находит пункт по пути из надписей,
  поэтому у страниц двух деревьев на одном уровне разные надписи. Страницу нельзя
  нажать; нажатие пункта на странице несёт его собственные `id` и `arg`. Страницы не считаются
  в 200 узлов дерева (их не больше 22). Билдер `.overflow(Overflow::Reject)`
  (`sortie::menu_tree::Overflow`) оставляет отказ `Error::Invalid` для такого уровня. В
  FakeDcs — `tree_level`, `press_tree_at` (нажатие по пути надписей), `FakeTreeEntry.page` и
  `menu_level` (что DCS показывает на уровне: пункты всех деревьев; FakeDcs, как DCS, находит
  пункт дерева по пути из надписей).
* Возможности движка (страница [Возможности движка](docs/capabilities.md)): одна таблица из
  типизированных операций, функций каталога DCS API (`call:<env>:<путь>`), результата пробника
  запущенной сборки DCS (`MISSING_IN_DCS`), выключателей владельца (`engine.toml
  [operations]`) и карантина. Она в `Start.capabilities`, в `Engine.Capabilities` и в
  `ctx.capabilities()` (одна запись — `ctx.capability(имя)`); изменения после `Start` приходят
  событием `CapabilityChanged` (ревизия событий 1). Имена — `sortie::caps`
  (`caps::SPAWN_STATIC`, `caps::call::mission::LAND_GET_HEIGHT`).
  `#[sortie::mission(requires = [..])]` — логика не подключится там, где нужного нет
  (`AttachRejected.missing_capabilities`). `Error::capability()` называет возможность отказа.
  Вид операции, во время которой упал DCS, уходит на карантин до снятия владельцем
  (`sortie caps --release`, `Engine.ReleaseQuarantine`); у универсального вызова на карантин
  уходит одна функция каталога (следующий пункт), она остаётся на карантине и на новой сборке
  DCS. Карантин типизированной операции снимает и
  другая сборка DCS, и он действует только на команды ревизии API 1: логика 0.1.0 его не
  замечает. Сборка DCS одна на процесс DCS: её называет связь хуков, иначе связь миссии;
  слово `unknown` (в окружении нет глобала с версией) сборкой не считается, поэтому оно не
  снимает карантин и не мешает ему появиться, когда второе окружение сборку знает; ту же
  сборку процесса отдают `Engine.Capabilities`, `Engine.Version` и `ServerStatus`. Слой Lua
  старше движка (без `sortie install`) показывает операции волны 1 как
  `NOT_IMPLEMENTED`. В Python — `EngineClient.capabilities` и `release_quarantine`.
* Журнал сбоев моста и карантин функции каталога: перед каждым вызовом каталога (и внутри
  пакета) мост записывает `call:<env>:<путь>` в `Logs/sortie-bridge.journal`; если DCS упал,
  на карантин уходит только эта функция (`Error::capability()` = `"call:mission:<путь>"`),
  без записи в журнале — функции пакета, который выполнялся; три сбоя моста на одной функции
  тоже. Медленный вызов — не падение: если мост отключил функцию только из-за вызовов дольше
  секунды, отказ действует до перезапуска DCS (заметка `Slow, not a crash`) и в хранилище
  ничего не записывается. Идентификатор команды может быть любым (длинный или с переводом
  строки журнал записывает в сокращённом виде с хешем), а процесс DCS движок отличает по
  `pid` и метке запуска моста, потому что Windows выдаёт `pid` повторно. Если DCS упал внутри
  испытания, журнал называет его, и больше ничего на карантин не уходит.
  `dcs_call`, другие функции и типизированные операции остаются `AVAILABLE`.
  Документированную функцию чтения без получателя движок при следующем старте миссии один раз
  вызывает с каноническими аргументами каталога (поле `canonical`): ответ снимает карантин.
  Испытание даётся один раз: движок хранит запись о пройденном испытании (она переживает его
  перезапуск), и функция, которая после этого снова дала сбой, остаётся на карантине без
  второго испытания, пока владелец не снимет его (снятие стирает и запись). Испытание не
  отправляется, пока универсальный вызов выключен владельцем, пока на карантине весь
  `dcs_call`, пока мост отказывает в вызове до перезапуска DCS и пока функции нет в этой
  сборке DCS; ответ, из которого видно, что DCS вызов не выполнял, ничего не решает, и
  испытание повторится при следующем старте миссии.
  Снимает его и `sortie caps --release call:mission:<путь>` (имя принимается и тогда, когда
  функции уже нет в каталоге, но её карантин записан). FakeDcs:
  `dcs.crash_inside("Object.getPoint")` роняет поддельный DCS внутри вызова. Нужны новые DLL
  моста и слой Lua (`sortie install`) и перезапуск DCS; старый мост работает, но без журнала
  (тогда на карантин уходит весь пакет).
* Карантин функции каталога, перенесённый с прежней сборки DCS (новая сборка его не снимает:
  сервер не должен второй раз упасть на том же вызове без решения человека), виден: заметка
  возможности называет сборку, на которой он записан («recorded on DCS …, carried over to the
  running build …»), `Engine.Health` перечисляет такие карантины в заметке и в новом поле
  `HealthResponse.carried_over_quarantines`. Снять их все — `sortie caps
  --release-carried-over`, новое поле `ReleaseQuarantineRequest.carried_over` (Python —
  `EngineClient.release_carried_over()`). Владелец движка может вернуть правило спецификации:
  `engine.toml [quarantine] clear_calls_on_new_build = true` (по умолчанию `false`) — тогда
  новая сборка DCS снимает и эти карантины.
* `engine.toml` задаёт и скорость спавна: `spawn_gate = { groups_per_s = 2, units_per_s = 24 }`
  (значения по умолчанию прежние).
* Защита каталога `span_300km` допустима только у записи ровно с двумя обязательными
  аргументами `vec2` или `vec3`; у другой записи (`[[calls.call]]` владельца в том числе) это
  ошибка при старте `sortied`. Вызов с такой защитой не уходит в DCS неизмеренным.
* Генератор: `sc.airbase(имя, ident=..., munitions={wsType: количество})` ограничивает боезапас
  склада аэродрома и задаёт начальный запас (wsType — четыре числа из `wsTypes.lua` игры,
  например `(4, 4, 7, 106)` для AIM-120C). Без `munitions` склад безлимитный, как раньше, а
  на безлимитном складе, по сообщениям, `add_item`, `remove_item` и `set_item` не меняют счёт
  (не измерено). Страница [Сценарий на Python](docs/generator.md#аэродромы-и-слоты-игроков).
* `THIRD-PARTY-NOTICES.txt` в корне репозитория SDK и `catalog/THIRD-PARTY-pydcs.txt`: таблица
  `catalog/static_types.toml` содержит только факты из базы pydcs 1.0.0 (LGPL-3.0-or-later):
  имя типа, категорию и модель; файл делает только генератор
  `python/sortie-gen/scripts/gen_static_types.py`, CI проверяет его ключом `--check`.

* `BatchReturn.cost_us`: время DCS, которое занял весь пакет `ctx.dcs().batch()` (один кадр).
* Общая форма событий (страница [Логика на Rust](docs/sdk.md), «События»): каждое событие из DCS
  называет свою запись `world.event` — `Event.dcs_event` (`v1::DcsEvent`), а запись, которой
  нет в перечислении, — `Event.dcs_name`. Так `S_EVENT_DEAD`, `S_EVENT_CRASH` и
  `S_EVENT_PILOT_DEAD` (все три — `Dead`) и `S_EVENT_TAKEOFF` / `S_EVENT_RUNWAY_TAKEOFF` (оба —
  `Takeoff`) различимы без новой ревизии событий. Фильтр `TypedEvents::from_dcs(..)` и
  `next_with_dcs_event()`. Событие DCS без своего типа (`Unknown`) несёт `ctx`
  (`v1::EventContext`): участники как снимки с Eid, место, тип оружия, текст, все остальные
  ключи DCS (`extra`) и объекты под другими ключами (`extra_objects`); `foreign` — событие
  другого скрипта миссии (`world.onEvent`). Фильтры `in_group` и `coalition` у `Unknown`
  смотрят на `ctx.initiator`. Слой Lua копирует все ключи события (раньше — 12) и читает
  участников облегчённо, по кэшу id. Палуба корабля как место события (`place`) — объект
  класса `Airbase` с id самого корабля: слой отдаёт её как аэродром и не кладёт в кэш, а
  `ctx.place` называет аэродром корабля и не меняет сам корабль (раньше после такого события
  корабль в мире становился наземным юнитом без группы). В FakeDcs —
  `FakeDcs::raise_event(FakeEvent::..)`.
* Eid оружия и катапультировавшихся пилотов (страница [Логика на Rust](docs/sdk.md), «Оружие и
  катапультировавшиеся пилоты»): `WeaponSnap.eid` в `Shot`, `Hit` и `Kill` одного оружия —
  один Eid; пилот и кресло в `Unknown.ctx` событий катапультирования — снимки с Eid. Они не
  сущности мира. `ctx.destroy(..)` убирает ракету в полёте и пилота по Eid (`Obj::weapon`,
  `Obj::snap`; возможность `destroy.weapon` теперь `AVAILABLE`). Универсальный вызов принимает
  оружие как получателя (чтения `Object.*`). В FakeDcs — `FakeDcs::{shoot, weapon_hit, eject,
  crew_landed, weapons, crew}`.
* `ctx.take_command_timings()` (модуль `sortie::timing`): сколько стоила каждая команда —
  `cost_us` внутри DCS и время от отправки до ответа (страница [Вызовы DCS](docs/dcs.md)).
* `Engine.Health`: у каждой связи `LinkHealth.fps` и `pump_p99_us` из последнего heartbeat моста
  (частота кадров и 99-й процентиль работы Sortie за один pump, мкс).

### Совместимость

* Движок этой версии работает только с мостом и слоем Lua этой версии (версия связи 1.1):
  после обновления `sortied` выполните `sortie install` и перезапустите DCS. Старый мост
  получает отказ с этой подсказкой при подключении, а не ошибки команд потом.
* Удаление метки `MarkCommand` логикой ревизии 0 после того, как метку удалил игрок на карте
  F10 (или движок не нашёл её после переподключения), снова успех, как в 0.1.0; `sortie::invalid`
  — только для имени, которое не ставилось или уже удалено командой. Текст ошибки — тот же, что у
  0.1.0 (`invalid command: mark ... has no DCS id yet`).
* Имена `MarkCommand` и `Menu` снова общие для сессии, как в 0.1.0: их удаление снимает запись,
  кто бы её ни поставил (логика или клиент `Commands.Submit`).
* `MarkCommand` теперь регистрируется как рисунок: повтор с тем же текстом и местом ничего не
  делает в DCS (0.1.0 вызывал `markToAll` ещё раз с тем же id), изменённый заменяет метку с
  новым id. Удаление несуществующей метки — успех (`ABSENT`) для логики, объявившей
  `api_rev = 1`; логика 0.1.0 (ревизия 0) получает `sortie::invalid`, как раньше. Метки и рисунки
  убираются при конце сессии, если в ней реестром пользовалась команда ревизии 1 или новее;
  сессия только логик 0.1.0 оставляет метки и меню, как 0.1.0.
* Логика 0.1.0 видит события и команды в DCS как раньше (проверка CMP-1): `UnitGone` с причиной
  `GONE_REASON_REPLACED` приходит ей как `GONE_REASON_DESPAWNED`; поток команд в DCS для
  `examples/op_north` совпадает с 0.1.0 побайтно.
* Мир: гибель пилота (`S_EVENT_PILOT_DEAD`) больше не делает юнит мёртвым — DCS присылает её,
  пока самолёт ещё летит; событие по-прежнему `Dead`. Логике API ревизии 0 (по умолчанию у
  `#[sortie::mission]`) оно приходит с `dead = true`, как в 0.1.0, и её мир (`ctx.world()`)
  держит юнит мёртвым, как в 0.1.0; живым его видит логика ревизии 1 и подписка на мир. Выход игрока из юнита (`S_EVENT_PLAYER_LEAVE_UNIT`) убирает игрока из
  `EntitySnap.player`: юнит пропадает из `players()` и из подписки на мир «только игроки», а
  `UnitGone.last_known` после выхода игрока не называет. Это видно и логике 0.1.0.
* `Unknown.fields` сохраняет вид 0.1.0: только прежние двенадцать ключей. Ключи DCS сверх них
  (`comment`, ключи новых сборок, объекты под другими ключами) есть только в `ctx`.
* `WeaponSnap.eid` больше не 0 (это видно и логике 0.1.0): по нему сопоставляются `Shot`, `Hit` и
  `Kill` одного оружия. Безымянный участник события, которого нет в мире (катапультировавшийся
  пилот, кресло), больше не попадает в мир движка; его снимок несёт Eid пилота. Реплика SDK
  этой версии не добавляет в мир ни оружие, ни такие объекты из событий.
* У `TypedEvents::of::<v1::Unknown>()` фильтры `in_group` и `coalition` теперь находят события
  (раньше у `Unknown` не было субъекта, и они не пропускали ничего).
* `Menu` (`ctx.menu(..)`) тоже регистрируется: в реплике мира — дерево из одного пункта с
  именем `sortie:menu/<ident>/..`; повтор ничего не делает, как и раньше; изменённая надпись
  заменяет пункт; ключ команды не используется. Исправлено:
  копия команды `.per_group()` снимается, когда слот группы пустеет, и ставится следующему
  игроку, в том числе в динамический слот с новым id группы (раньше слой Lua помнил каждый id
  группы навсегда и не ставил команду заново).
* `sortie::Failure` получил поле `capability`: код, который собирает `Failure { .. }` без
  `..Failure::default()`, должен его добавить.
* Сырые вызовы `trigger.action.markTo*` / `*ToAll` / `setMarkup*` / `removeMark` есть в
  каталоге, но устарели в пользу `ctx.map()` и отклоняют id от 7 100 000.
* `GroupSel` и `UnitSel` переехали из `commands.proto` в `common.proto` (пакет `sortie.v1`,
  номера полей те же, проводной формат не изменился). В Rust пути прежние
  (`sortie::proto::v1::GroupSel`); в Python стабы теперь в `common_pb2`, а не в `commands_pb2`.
  `buf breaking` проверяет совместимость на уровне пакета.

### Безопасность

* Слой Lua при старте миссии выключает модальное окно ошибок Lua DCS
  (`env.setErrorMessageBoxEnabled(false)`): ошибка в любом скрипте миссии больше не
  останавливает выделенный сервер до щелчка по окну.
* Вызовы DCS: ключи перечислений проверяются везде, где стоят, и внутри таблиц: форма
  `<таблица>.<КЛЮЧ>`, таблица — одна из названных каталогом (`world.VolumeType` для объёмов);
  у параметра `any` ключей нет; в окружении хуков — только таблицы слоя `sortie.*`. Слой
  принимает путь только целиком. Пакет `ctx.dcs().batch()` оплачивает в лимите писателя каждый
  вызов. Предел в 256 созданных объектов (лазерных пятен) на сессию проверяется до вызова DCS:
  отклонённый вызов не оставляет в DCS пятна, которое никто не снимет.
* Запись `[[calls.call]]` владельца с классом `heavy` и именем не из get/is/has считается
  изменяющей и выключена, пока её не включат (`enabled = true` или `sortied --dev`).
  `sortied --dev` теперь действительно включает изменяющие записи владельца (раньше включал
  только встроенные, а отказ советовал `--dev`); `enabled = false` записи и список `disable`
  сильнее `--dev`.
* `net().player_info(id, атрибут)` принимает только атрибуты `id`, `name`, `side`, `slot`,
  `ping`, `ucid`, `lang`: другое имя — `Error::Invalid`, `ipaddr` — по-прежнему
  `Error::Rejected`. Раньше отклонялась одна точная строка `ipaddr`, а строка вроде
  `"ipaddr\0"` доходила до DCS; как DCS читает такое имя, неизвестно.
* `engine.toml` `[calls]`: в `enable` и `disable` метод называется путём своей записи каталога
  (`Object.destroy`). Имя через класс-наследник (`Unit.destroy`, `Weapon.destroy`) раньше молча
  переключало запись для всех классов; теперь это ошибка при старте `sortied`, в сообщении
  названа запись.
* Мост не передаёт результат, который не смог преобразовать целиком (больше 200 000 значений
  или 16 МиБ строк): команда получает `sortie::bridge_fault` с этим объяснением, а не
  результат с пропусками. Нужны новые DLL моста и слой Lua (`sortie install`, перезапуск DCS).

* Сырые таблицы больше не несут код в DCS. `Task::raw(..)`, `.raw(..)` статика и аргументы
  `ctx.dcs()` с `id = "Script"` / `"ScriptFile"`, строкой `condition` (условие
  `ControlledTask`), строкой `command` в `params` или строкой `file` отклоняются с
  `sortie::rejected`, `capability = "dev_eval"`, и путём внутри таблицы. Это касается и логик
  0.1.0: в 0.1.0 такая задача выполняла Lua в DCS без `--dev-eval`. NaN и бесконечность в сырых
  таблицах и в числах команд 0.1.0 (точка спавна, орбита, дым, метка, высота земли) теперь
  `sortie::invalid` (раньше молча превращались в `null` или в значение по умолчанию). С
  `sortied --dev-eval` код из команды токена `admin` проходит с предупреждением в журнале
  ([Проверка сырых таблиц](docs/operations.md#проверка-сырых-таблиц)).
* `engine.toml` `[calls]` строже: нельзя расширить встроенный `clamp`, поменять поля, из которых
  генерируются обёртки, закрыть унаследованный метод новой записью (`Unit.destroy`) и добавить
  путь не от таблиц DCS (`_G`, `string`); `_G` в списке NEVER. Такой файл останавливает
  `sortied` при старте.

## [0.1.0] — 2026-11-09

Первый выпуск Sortie SDK.

### Что есть

* Крейт `sortie`: логика миссии как асинхронная программа на Rust. `#[sortie::mission]` и
  `sortie::main!` дают точку входа и весь `main.rs`. Через `Ctx` логика читает мир из локальной
  реплики (`ctx.wait_until(|w| ...)`, события) и отдаёт команды: сообщения, флаги, опции и
  задачи групп, спавн по шаблонам, меню F10, дым. Есть состояние в движке, таймеры и
  `once_per_turn`. Каждая команда — future, который завершается, когда DCS её выполнила;
  ошибки называют строку вызова.
* `sortie-build` и `sortie::include_scenario!`: типизированные символы сценария из
  `scenario.lock.json` (`groups::...`, `zones::...`, `templates::...`, `flags::...`). Опечатка в
  имени — ошибка компиляции, а не сбой в DCS.
* Генератор `sortie-gen` (Python 3.11+, pydcs 1.0.0): сценарий в коде, `.miz`, manifest и lock;
  регистрация и запуск сборок у движка, поток событий, итоги сессии; команды `lobby` и `adopt`.
* Схемы protobuf `sortie.v1` (API движка) и `sortie.manifest.v1`.
* Шаблон проекта миссии (`template/`) и пример `examples/op_north`.
* Документация на русском, навыки для ИИ-агентов (`agents/`) и сайт с документацией.

### Чего пока нет

* Тестов логики без DCS. `#[sortie::test]` и FakeDcs появятся в SDK 0.2; сейчас
  `#[sortie::test]` даёт ошибку компиляции с пояснением. Логику проверяют на живой DCS с
  `sortied --dev`.
* Горячей перезагрузки логики (`sortie dev`).

### Совместимость

* Движок поставляется отдельно: архив `sortie-runtime-0.1.0-win64.zip` в релизе `v0.1.0`.
  Используйте SDK и движок одной версии. Там же колесо генератора
  `sortie_gen-0.1.0-py3-none-any.whl` и `SHA256SUMS` с контрольными суммами обоих файлов.
* Rust stable 1.89 и новее (edition 2024); на Windows нужен линкер MSVC. Python 3.11 и новее
  для генератора.
