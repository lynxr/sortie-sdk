# Изменения

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии — по
[SemVer](https://semver.org/lang/ru/). До 1.0 API может меняться между минорными версиями; каждое
такое изменение описано здесь.

## [0.2.0] — 2026-11-17

Основа широкого API (волна 1, ревизия API 1). Логика 0.1.0 работает без изменений.

### Добавлено

* Общий словарь в `sortie.v1` (`common.proto`): селекторы `ObjSel`, `AirbaseSel`, `PlayerSel`,
  `WarehouseSel`, `ZoneSel`, `ControllerSel`, `Audience`, место `Anchor`, области `MapArea` и
  объёмы `Volume`, `Rgba`, `Modulation`, `NameConflict`, описание возможностей `Capability`.
  В SDK — модуль `sortie::sel` с `From` из уже знакомых ручек (`Eid`, `&Group<K>`,
  `GroupRef`, `AirbaseRef`, `ZoneRef`, `Vec3`, `MapPoint`, `Coalition`).
* Типизированный ответ команды: `CommandResult.reply` (снимки созданного и удалённого),
  `world_rev` (ревизия мира с эффектом команды) и `replayed` (ответ на повтор по ключу).
  SDK кладёт снимки ответа в реплику сразу: после `spawn_group(..).await?` группа видна в
  `ctx.world()` до следующего тика.
* Ревизии объявляет логика: `#[sortie::mission(api_rev = 1, event_rev = 0)]` (по умолчанию 0 и
  0 — поведение 0.1.0). `ctx.engine_api_rev()`, `ctx.event_rev()`, `ctx.writer()` говорят, что
  ответил движок. Операция новее объявленной ревизии — `Error::Revision`, новее движка —
  `Error::EngineTooOld`; в обоих случаях ничего не отправлено.
* `Engine.Version` отдаёт `api_rev`.
* Вызовы DCS (ревизия API 1): каталог DCS API `catalog/dcs_api.toml` и типизированные обёртки
  из него — `ctx.dcs().land().surface_type(p)`, `ctx.dcs().airbase(a).set_coalition(c)`,
  `ctx.dcs().warehouse(w).add_item(..)`, лазерные пятна, звуки из `.miz`, чтения хуков `net.*`
  (страница [Вызовы DCS](docs/dcs.md), список — [справочник каталога](docs/dcs-catalog.md)).
  Движок проверяет каждый вызов по каталогу до DCS; изменяющие функции выключены, пока владелец
  движка не включит их в `<Saved Games>/Sortie/engine.toml` (`[calls]`) или не запустит
  `sortied --dev`. Чтение не берёт ключ. Команды `DcsCall` и `DcsBatch`, ответ `Reply.call` /
  `Reply.batch`. Вызов по строке пути и пакеты — за cargo-фичей `dcs-raw`. В Python — модуль
  `sortie_gen.dcs_api` поверх `EngineClient.dcs_call`. Метод объекта выполняется через таблицу
  класса самого объекта, как `unit:getCoalition()`: класс `CoalitionObject` есть только в
  документации DCS, в игре такой таблицы нет, поэтому `coalition()` и `country()` работают у
  юнита, статика, аэродрома и оружия. `land().profile(a, b)` берёт два `Vec3` (DCS читает у
  них `x` и `z`). Число, которое DCS вернул строкой (id объекта в 2.9.31), приходит числом:
  `static_object(..).id()`, `airbase(..).id()`, `group(..).id()`.
  `static_object(..).cargo_display_name()`, как и `cargo_weight()`, движок выполняет только
  для груза (`Error::Invalid` для другого статика: по описанию DCS на нём падает).
  Повтор вызова с ключом возвращает сохранённый результат вместе с объектами и дескрипторами:
  `spots().create_laser(..).key("lase-1")` после перезапуска логики в той же сессии отдаёт тот
  же `Handle` (раньше повтор заканчивался `Error::Invalid`, и пятно нельзя было убрать до
  конца сессии). Состояние объектов в ответе на повтор читается из мира заново. Под ключом не
  хранятся только значения результата больше 64 КиБ: повтор такого вызова — новая ошибка
  `Error::ResultNotKept` (`sortie::result_not_kept`), в Python — `errors.ResultNotKept`.
  Аргумент-объект, его id или имя проверяется на класс параметра и тогда, когда он задан
  дескриптором или результатом предыдущего вызова пакета: `Spot.createLaser` с пятном вместо
  источника или id юнита там, где нужен id группы, — `Error::Invalid`, DCS не вызывается
  (раньше такой вызов уходил в DCS). Таблица в результате приходит целиком или значением
  `Value::Cut(n)` с `truncated`; ответ одной команды, все вызовы пакета вместе, — не больше
  150 000 значений (раньше большой пакет чтений терял все результаты с ошибкой
  `sortie::bridge_fault` «does not decode»).
* Объекты (ревизия API 1, страница [Объекты](docs/objects.md)): `ctx.spawn_static(тип, страна)`
  — статик, груз или рабочий FARP (`.heliport(..)`), с политикой имени `.on_conflict(..)`
  (`Fail`, `Keep`, `Replace`); категорию и модель DCS движок берёт из таблицы типов
  `catalog/static_types.toml` (её генерирует sortie-gen из базы pydcs). Статик сразу в мире,
  событие `Birth` с `synthesised = true`. `ctx.destroy(obj)` уничтожает любой юнит, статик или
  груз; юнит с игроком — только с `.allow_player()` (так же `group.destroy()` при ревизии 1).
  `ctx.remove_junk(объёмы)` убирает обломки и воронки. Протокол: `SpawnStatic`,
  `Destroy.object` / `allow_player`, `RemoveJunk`, `Reply.junk`, `Birth.synthesised`,
  `GONE_REASON_REPLACED`. Обёртки `object(..).destroy()` и `world().remove_junk(..)` каталога
  помечены устаревшими в пользу этих операций. `Keep` для FARP возвращает и его аэродром
  (`SpawnedStatic::airbase`), как при постановке. После `destroy()` статика или груза слой
  Lua в следующих кадрах DCS (не дольше десяти) смотрит, исчез ли объект: по сообщениям, DCS не убирает FARP
  (не измерено). Если объект остался, `ctx.destroy(..)` и `Replace` отвечают `Error::Lua`
  («DCS did not remove …»), мир считает статик и его аэродром живыми, второй FARP поверх
  первого не ставится. Ответ на уничтожение статика приходит, когда объект исчез (обычно на кадр позже); юниты,
  группы и оружие — как раньше. В FakeDcs — `dcs.survives_destroy(имя, true)`. Юнит с категорией
  `Structure` (вооружённое строение в наземной группе) адресуется по Eid как юнит:
  раньше `ctx.destroy(eid)`, якорь и получатель вызова отвечали `Error::Gone`, а `UnitSel` —
  `Error::Invalid`.
* Пакет спавнов (ревизия API 1, страница [Объекты](docs/objects.md#пакет-спавнов)):
  `ctx.spawn_batch()` — много групп и статиков одной командой с одним ключом (восстановление
  кампании). Движок проверяет весь пакет до отправки (имя, занятое в мире, — ошибка
  `NAME_CONFLICT` только этого элемента), ограничитель спавна раздаёт элементы по времени по
  очереди с другими спавнами, ничего не откатывается; `.stop_on_error()`, типизированный результат элемента
  `out.get(&slot)`. Повтор после обрыва связи с тем же ключом продолжает пакет: найденные по
  имени элементы помечены `settled`, ни один не ставится дважды. Протокол: `SpawnBatch`
  (`Command.body.spawn_batch = 35`), `SpawnItem`, `SpawnResult`, `Reply.spawns`; возможность
  `spawn_batch`.
* Реестр ресурсов и рисунки на карте (ревизия API 1): `ctx.map()` — метки с текстом, линии,
  ломаные, многоугольники, круги, прямоугольники, стрелки и надписи по имени (страница
  [Рисование на карте](docs/map.md)). Повтор с тем же описанием не идёт в DCS, цвет, заливка,
  радиус, текст и крайние точки меняются на месте, остальное перерисовывается. Команды
  `ResourcePut` / `ResourceRemove` (`resources.proto`), ответ `Reply.resource`, реестр в мире
  (`WorldSnapshot.resources`, `WorldDelta.resource_upserts` / `resource_removals`,
  `ctx.world().resources()`), событие `ResourceEnded` (ревизия событий 1), у событий `Mark`
  поля `name` и `own`. Движок отдаёт ревизию событий 1.
* Деревья меню F10 (ревизия API 1, страница [Деревья меню F10](docs/menus.md)):
  `ctx.menus().tree(имя)` — пункты и подменю для всех, коалиции или одной группы, по имени.
  Повтор того же дерева не идёт в DCS, при изменении движок убирает и добавляет только
  изменённые пункты. Меню группы следует за слотом: пока в группе нет игрока, дерево
  приостановлено (`SUSPENDED`), движок ставит его, когда игрок занял слот, убирает, когда слот
  опустел, и ставит заново для нового id группы (динамические слоты). Двух пунктов с одной
  надписью на уровне быть не может. Нажатие несёт дерево, `id` пункта и его `arg`
  (`MenuPressed.tree`, `item`, `arg`, ревизия событий 1). Протокол: `MenuTree`, `MenuNode`,
  `MenuOverflow`, `ResourcePut.spec.menu_tree`.
* Страницы меню (`MENU_OVERFLOW_PAGE`, по умолчанию): уровень дерева длиннее 10 пунктов DCS
  показывает как 9 пунктов и подменю `More...` с остальными, и так дальше. Страница
  корневого уровня дерева называется `More... (<имя дерева>)`: этот уровень дерево делит с
  другими деревьями и командами меню из сценария, а DCS находит пункт по пути из надписей,
  поэтому у страниц двух деревьев на одном уровне разные надписи. Страницу нельзя
  нажать; нажатие пункта на странице несёт его собственные `id` и `arg`. Страницы не считаются
  в 200 узлов дерева (их не больше 22). Билдер `.overflow(Overflow::Reject)`
  (`sortie::menu_tree::Overflow`) оставляет отказ `Error::Invalid` для такого уровня. В
  FakeDcs — `tree_level`, `press_tree_at` (нажатие по пути надписей), `FakeTreeEntry.page` и
  `menu_level` (что DCS показывает на уровне: пункты всех деревьев; FakeDcs, как DCS, находит
  пункт дерева по пути из надписей).
* Возможности движка (страница [Возможности движка](docs/capabilities.md)): одна таблица из
  типизированных операций, функций каталога DCS API (`call:<env>:<путь>`), результата пробника
  запущенной сборки DCS (`MISSING_IN_DCS`), выключателей владельца (`engine.toml
  [operations]`) и карантина. Она в `Start.capabilities`, в `Engine.Capabilities` и в
  `ctx.capabilities()` (одна запись — `ctx.capability(имя)`); изменения после `Start` приходят
  событием `CapabilityChanged` (ревизия событий 1). Имена — `sortie::caps`
  (`caps::SPAWN_STATIC`, `caps::call::mission::LAND_GET_HEIGHT`).
  `#[sortie::mission(requires = [..])]` — логика не подключится там, где нужного нет
  (`AttachRejected.missing_capabilities`). `Error::capability()` называет возможность отказа.
  Вид операции, во время которой упал DCS, уходит на карантин до снятия владельцем
  (`sortie caps --release`, `Engine.ReleaseQuarantine`); у универсального вызова на карантин
  уходит одна функция каталога (следующий пункт), она остаётся на карантине и на новой сборке
  DCS. Карантин типизированной операции снимает и
  другая сборка DCS, и он действует только на команды ревизии API 1: логика 0.1.0 его не
  замечает. Сборка DCS одна на процесс DCS: её называет связь хуков, иначе связь миссии;
  слово `unknown` (в окружении нет глобала с версией) сборкой не считается, поэтому оно не
  снимает карантин и не мешает ему появиться, когда второе окружение сборку знает; ту же
  сборку процесса отдают `Engine.Capabilities`, `Engine.Version` и `ServerStatus`. Слой Lua
  старше движка (без `sortie install`) показывает операции волны 1 как
  `NOT_IMPLEMENTED`. В Python — `EngineClient.capabilities` и `release_quarantine`.
* Журнал сбоев моста и карантин функции каталога: перед каждым вызовом каталога (и внутри
  пакета) мост записывает `call:<env>:<путь>` в `Logs/sortie-bridge.journal`; если DCS упал,
  на карантин уходит только эта функция (`Error::capability()` = `"call:mission:<путь>"`),
  без записи в журнале — функции пакета, который выполнялся; три сбоя моста на одной функции
  тоже. Медленный вызов — не падение: если мост отключил функцию только из-за вызовов дольше
  секунды, отказ действует до перезапуска DCS (заметка `Slow, not a crash`) и в хранилище
  ничего не записывается. Идентификатор команды может быть любым (длинный или с переводом
  строки журнал записывает в сокращённом виде с хешем), а процесс DCS движок отличает по
  `pid` и метке запуска моста, потому что Windows выдаёт `pid` повторно. Если DCS упал внутри
  испытания, журнал называет его, и больше ничего на карантин не уходит.
  `dcs_call`, другие функции и типизированные операции остаются `AVAILABLE`.
  Документированную функцию чтения без получателя движок при следующем старте миссии один раз
  вызывает с каноническими аргументами каталога (поле `canonical`): ответ снимает карантин.
  Испытание даётся один раз: движок хранит запись о пройденном испытании (она переживает его
  перезапуск), и функция, которая после этого снова дала сбой, остаётся на карантине без
  второго испытания, пока владелец не снимет его (снятие стирает и запись). Испытание не
  отправляется, пока универсальный вызов выключен владельцем, пока на карантине весь
  `dcs_call`, пока мост отказывает в вызове до перезапуска DCS и пока функции нет в этой
  сборке DCS; ответ, из которого видно, что DCS вызов не выполнял, ничего не решает, и
  испытание повторится при следующем старте миссии.
  Снимает его и `sortie caps --release call:mission:<путь>` (имя принимается и тогда, когда
  функции уже нет в каталоге, но её карантин записан). FakeDcs:
  `dcs.crash_inside("Object.getPoint")` роняет поддельный DCS внутри вызова. Нужны новые DLL
  моста и слой Lua (`sortie install`) и перезапуск DCS; старый мост работает, но без журнала
  (тогда на карантин уходит весь пакет).
* Карантин функции каталога, перенесённый с прежней сборки DCS (новая сборка его не снимает:
  сервер не должен второй раз упасть на том же вызове без решения человека), виден: заметка
  возможности называет сборку, на которой он записан («recorded on DCS …, carried over to the
  running build …»), `Engine.Health` перечисляет такие карантины в заметке и в новом поле
  `HealthResponse.carried_over_quarantines`. Снять их все — `sortie caps
  --release-carried-over`, новое поле `ReleaseQuarantineRequest.carried_over` (Python —
  `EngineClient.release_carried_over()`). Владелец движка может вернуть правило спецификации:
  `engine.toml [quarantine] clear_calls_on_new_build = true` (по умолчанию `false`) — тогда
  новая сборка DCS снимает и эти карантины.
* `engine.toml` задаёт и скорость спавна: `spawn_gate = { groups_per_s = 2, units_per_s = 24 }`
  (значения по умолчанию прежние).
* Защита каталога `span_300km` допустима только у записи ровно с двумя обязательными
  аргументами `vec2` или `vec3`; у другой записи (`[[calls.call]]` владельца в том числе) это
  ошибка при старте `sortied`. Вызов с такой защитой не уходит в DCS неизмеренным.
* Генератор: `sc.airbase(имя, ident=..., munitions={wsType: количество})` ограничивает боезапас
  склада аэродрома и задаёт начальный запас (wsType — четыре числа из `wsTypes.lua` игры,
  например `(4, 4, 7, 106)` для AIM-120C). Без `munitions` склад безлимитный, как раньше, а
  на безлимитном складе, по сообщениям, `add_item`, `remove_item` и `set_item` не меняют счёт
  (не измерено). Страница [Сценарий на Python](docs/generator.md#аэродромы-и-слоты-игроков).
* `THIRD-PARTY-NOTICES.txt` в корне репозитория SDK и `catalog/THIRD-PARTY-pydcs.txt`: таблица
  `catalog/static_types.toml` содержит только факты из базы pydcs 1.0.0 (LGPL-3.0-or-later):
  имя типа, категорию и модель; файл делает только генератор
  `python/sortie-gen/scripts/gen_static_types.py`, CI проверяет его ключом `--check`.

* `BatchReturn.cost_us`: время DCS, которое занял весь пакет `ctx.dcs().batch()` (один кадр).
* Общая форма событий (страница [Логика на Rust](docs/sdk.md), «События»): каждое событие из DCS
  называет свою запись `world.event` — `Event.dcs_event` (`v1::DcsEvent`), а запись, которой
  нет в перечислении, — `Event.dcs_name`. Так `S_EVENT_DEAD`, `S_EVENT_CRASH` и
  `S_EVENT_PILOT_DEAD` (все три — `Dead`) и `S_EVENT_TAKEOFF` / `S_EVENT_RUNWAY_TAKEOFF` (оба —
  `Takeoff`) различимы без новой ревизии событий. Фильтр `TypedEvents::from_dcs(..)` и
  `next_with_dcs_event()`. Событие DCS без своего типа (`Unknown`) несёт `ctx`
  (`v1::EventContext`): участники как снимки с Eid, место, тип оружия, текст, все остальные
  ключи DCS (`extra`) и объекты под другими ключами (`extra_objects`); `foreign` — событие
  другого скрипта миссии (`world.onEvent`). Фильтры `in_group` и `coalition` у `Unknown`
  смотрят на `ctx.initiator`. Слой Lua копирует все ключи события (раньше — 12) и читает
  участников облегчённо, по кэшу id. Палуба корабля как место события (`place`) — объект
  класса `Airbase` с id самого корабля: слой отдаёт её как аэродром и не кладёт в кэш, а
  `ctx.place` называет аэродром корабля и не меняет сам корабль (раньше после такого события
  корабль в мире становился наземным юнитом без группы). В FakeDcs —
  `FakeDcs::raise_event(FakeEvent::..)`.
* Eid оружия и катапультировавшихся пилотов (страница [Логика на Rust](docs/sdk.md), «Оружие и
  катапультировавшиеся пилоты»): `WeaponSnap.eid` в `Shot`, `Hit` и `Kill` одного оружия —
  один Eid; пилот и кресло в `Unknown.ctx` событий катапультирования — снимки с Eid. Они не
  сущности мира. `ctx.destroy(..)` убирает ракету в полёте и пилота по Eid (`Obj::weapon`,
  `Obj::snap`; возможность `destroy.weapon` теперь `AVAILABLE`). Универсальный вызов принимает
  оружие как получателя (чтения `Object.*`). В FakeDcs — `FakeDcs::{shoot, weapon_hit, eject,
  crew_landed, weapons, crew}`.
* `ctx.take_command_timings()` (модуль `sortie::timing`): сколько стоила каждая команда —
  `cost_us` внутри DCS и время от отправки до ответа (страница [Вызовы DCS](docs/dcs.md)).
* `Engine.Health`: у каждой связи `LinkHealth.fps` и `pump_p99_us` из последнего heartbeat моста
  (частота кадров и 99-й процентиль работы Sortie за один pump, мкс).

### Совместимость

* Движок этой версии работает только с мостом и слоем Lua этой версии (версия связи 1.1):
  после обновления `sortied` выполните `sortie install` и перезапустите DCS. Старый мост
  получает отказ с этой подсказкой при подключении, а не ошибки команд потом.
* Удаление метки `MarkCommand` логикой ревизии 0 после того, как метку удалил игрок на карте
  F10 (или движок не нашёл её после переподключения), снова успех, как в 0.1.0; `sortie::invalid`
  — только для имени, которое не ставилось или уже удалено командой. Текст ошибки — тот же, что у
  0.1.0 (`invalid command: mark ... has no DCS id yet`).
* Имена `MarkCommand` и `Menu` снова общие для сессии, как в 0.1.0: их удаление снимает запись,
  кто бы её ни поставил (логика или клиент `Commands.Submit`).
* `MarkCommand` теперь регистрируется как рисунок: повтор с тем же текстом и местом ничего не
  делает в DCS (0.1.0 вызывал `markToAll` ещё раз с тем же id), изменённый заменяет метку с
  новым id. Удаление несуществующей метки — успех (`ABSENT`) для логики, объявившей
  `api_rev = 1`; логика 0.1.0 (ревизия 0) получает `sortie::invalid`, как раньше. Метки и рисунки
  убираются при конце сессии, если в ней реестром пользовалась команда ревизии 1 или новее;
  сессия только логик 0.1.0 оставляет метки и меню, как 0.1.0.
* Логика 0.1.0 видит события и команды в DCS как раньше (проверка CMP-1): `UnitGone` с причиной
  `GONE_REASON_REPLACED` приходит ей как `GONE_REASON_DESPAWNED`; поток команд в DCS для
  `examples/op_north` совпадает с 0.1.0 побайтно.
* Мир: гибель пилота (`S_EVENT_PILOT_DEAD`) больше не делает юнит мёртвым — DCS присылает её,
  пока самолёт ещё летит; событие по-прежнему `Dead`. Логике API ревизии 0 (по умолчанию у
  `#[sortie::mission]`) оно приходит с `dead = true`, как в 0.1.0, и её мир (`ctx.world()`)
  держит юнит мёртвым, как в 0.1.0; живым его видит логика ревизии 1 и подписка на мир. Выход игрока из юнита (`S_EVENT_PLAYER_LEAVE_UNIT`) убирает игрока из
  `EntitySnap.player`: юнит пропадает из `players()` и из подписки на мир «только игроки», а
  `UnitGone.last_known` после выхода игрока не называет. Это видно и логике 0.1.0.
* `Unknown.fields` сохраняет вид 0.1.0: только прежние двенадцать ключей. Ключи DCS сверх них
  (`comment`, ключи новых сборок, объекты под другими ключами) есть только в `ctx`.
* `WeaponSnap.eid` больше не 0 (это видно и логике 0.1.0): по нему сопоставляются `Shot`, `Hit` и
  `Kill` одного оружия. Безымянный участник события, которого нет в мире (катапультировавшийся
  пилот, кресло), больше не попадает в мир движка; его снимок несёт Eid пилота. Реплика SDK
  этой версии не добавляет в мир ни оружие, ни такие объекты из событий.
* У `TypedEvents::of::<v1::Unknown>()` фильтры `in_group` и `coalition` теперь находят события
  (раньше у `Unknown` не было субъекта, и они не пропускали ничего).
* `Menu` (`ctx.menu(..)`) тоже регистрируется: в реплике мира — дерево из одного пункта с
  именем `sortie:menu/<ident>/..`; повтор ничего не делает, как и раньше; изменённая надпись
  заменяет пункт; ключ команды не используется. Исправлено:
  копия команды `.per_group()` снимается, когда слот группы пустеет, и ставится следующему
  игроку, в том числе в динамический слот с новым id группы (раньше слой Lua помнил каждый id
  группы навсегда и не ставил команду заново).
* `sortie::Failure` получил поле `capability`: код, который собирает `Failure { .. }` без
  `..Failure::default()`, должен его добавить.
* Сырые вызовы `trigger.action.markTo*` / `*ToAll` / `setMarkup*` / `removeMark` есть в
  каталоге, но устарели в пользу `ctx.map()` и отклоняют id от 7 100 000.
* `GroupSel` и `UnitSel` переехали из `commands.proto` в `common.proto` (пакет `sortie.v1`,
  номера полей те же, проводной формат не изменился). В Rust пути прежние
  (`sortie::proto::v1::GroupSel`); в Python стабы теперь в `common_pb2`, а не в `commands_pb2`.
  `buf breaking` проверяет совместимость на уровне пакета.

### Безопасность

* Слой Lua при старте миссии выключает модальное окно ошибок Lua DCS
  (`env.setErrorMessageBoxEnabled(false)`): ошибка в любом скрипте миссии больше не
  останавливает выделенный сервер до щелчка по окну.
* Вызовы DCS: ключи перечислений проверяются везде, где стоят, и внутри таблиц: форма
  `<таблица>.<КЛЮЧ>`, таблица — одна из названных каталогом (`world.VolumeType` для объёмов);
  у параметра `any` ключей нет; в окружении хуков — только таблицы слоя `sortie.*`. Слой
  принимает путь только целиком. Пакет `ctx.dcs().batch()` оплачивает в лимите писателя каждый
  вызов. Предел в 256 созданных объектов (лазерных пятен) на сессию проверяется до вызова DCS:
  отклонённый вызов не оставляет в DCS пятна, которое никто не снимет.
* Запись `[[calls.call]]` владельца с классом `heavy` и именем не из get/is/has считается
  изменяющей и выключена, пока её не включат (`enabled = true` или `sortied --dev`).
  `sortied --dev` теперь действительно включает изменяющие записи владельца (раньше включал
  только встроенные, а отказ советовал `--dev`); `enabled = false` записи и список `disable`
  сильнее `--dev`.
* `net().player_info(id, атрибут)` принимает только атрибуты `id`, `name`, `side`, `slot`,
  `ping`, `ucid`, `lang`: другое имя — `Error::Invalid`, `ipaddr` — по-прежнему
  `Error::Rejected`. Раньше отклонялась одна точная строка `ipaddr`, а строка вроде
  `"ipaddr\0"` доходила до DCS; как DCS читает такое имя, неизвестно.
* `engine.toml` `[calls]`: в `enable` и `disable` метод называется путём своей записи каталога
  (`Object.destroy`). Имя через класс-наследник (`Unit.destroy`, `Weapon.destroy`) раньше молча
  переключало запись для всех классов; теперь это ошибка при старте `sortied`, в сообщении
  названа запись.
* Мост не передаёт результат, который не смог преобразовать целиком (больше 200 000 значений
  или 16 МиБ строк): команда получает `sortie::bridge_fault` с этим объяснением, а не
  результат с пропусками. Нужны новые DLL моста и слой Lua (`sortie install`, перезапуск DCS).

* Сырые таблицы больше не несут код в DCS. `Task::raw(..)`, `.raw(..)` статика и аргументы
  `ctx.dcs()` с `id = "Script"` / `"ScriptFile"`, строкой `condition` (условие
  `ControlledTask`), строкой `command` в `params` или строкой `file` отклоняются с
  `sortie::rejected`, `capability = "dev_eval"`, и путём внутри таблицы. Это касается и логик
  0.1.0: в 0.1.0 такая задача выполняла Lua в DCS без `--dev-eval`. NaN и бесконечность в сырых
  таблицах и в числах команд 0.1.0 (точка спавна, орбита, дым, метка, высота земли) теперь
  `sortie::invalid` (раньше молча превращались в `null` или в значение по умолчанию). С
  `sortied --dev-eval` код из команды токена `admin` проходит с предупреждением в журнале
  ([Проверка сырых таблиц](docs/operations.md#проверка-сырых-таблиц)).
* `engine.toml` `[calls]` строже: нельзя расширить встроенный `clamp`, поменять поля, из которых
  генерируются обёртки, закрыть унаследованный метод новой записью (`Unit.destroy`) и добавить
  путь не от таблиц DCS (`_G`, `string`); `_G` в списке NEVER. Такой файл останавливает
  `sortied` при старте.

## [0.1.0] — 2026-11-09

Первый выпуск Sortie SDK.

### Что есть

* Крейт `sortie`: логика миссии как асинхронная программа на Rust. `#[sortie::mission]` и
  `sortie::main!` дают точку входа и весь `main.rs`. Через `Ctx` логика читает мир из локальной
  реплики (`ctx.wait_until(|w| ...)`, события) и отдаёт команды: сообщения, флаги, опции и
  задачи групп, спавн по шаблонам, меню F10, дым. Есть состояние в движке, таймеры и
  `once_per_turn`. Каждая команда — future, который завершается, когда DCS её выполнила;
  ошибки называют строку вызова.
* `sortie-build` и `sortie::include_scenario!`: типизированные символы сценария из
  `scenario.lock.json` (`groups::...`, `zones::...`, `templates::...`, `flags::...`). Опечатка в
  имени — ошибка компиляции, а не сбой в DCS.
* Генератор `sortie-gen` (Python 3.11+, pydcs 1.0.0): сценарий в коде, `.miz`, manifest и lock;
  регистрация и запуск сборок у движка, поток событий, итоги сессии; команды `lobby` и `adopt`.
* Схемы protobuf `sortie.v1` (API движка) и `sortie.manifest.v1`.
* Шаблон проекта миссии (`template/`) и пример `examples/op_north`.
* Документация на русском, навыки для ИИ-агентов (`agents/`) и сайт с документацией.

### Чего пока нет

* Тестов логики без DCS. `#[sortie::test]` и FakeDcs появятся в SDK 0.2; сейчас
  `#[sortie::test]` даёт ошибку компиляции с пояснением. Логику проверяют на живой DCS с
  `sortied --dev`.
* Горячей перезагрузки логики (`sortie dev`).

### Совместимость

* Движок поставляется отдельно: архив `sortie-runtime-0.1.0-win64.zip` в релизе `v0.1.0`.
  Используйте SDK и движок одной версии. Там же колесо генератора
  `sortie_gen-0.1.0-py3-none-any.whl` и `SHA256SUMS` с контрольными суммами обоих файлов.
* Rust stable 1.89 и новее (edition 2024); на Windows нужен линкер MSVC. Python 3.11 и новее
  для генератора.
